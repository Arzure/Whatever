## 第 1 课：一次点击的完整旅程（架构总览）

以推理杀模式点击『听取所有存活者发言』为例，数据流是这样的：

```
你的浏览器（Vue 组件）
   │  ① fetch POST /api/game/:id/action
   ▼
Express 后端（server/index.js 路由）
   │  ② 找到存档 → 调用模式处理器
   ▼
推理杀引擎（server/modes/deduction.js）
   │  ③ 逐个角色调用 LLM 生成发言
   │  ④ 程序结算夜晚/处刑逻辑
   ▼
SQLite（data/game.db）
   │  ⑤ 写回存档
   ▼
响应 JSON → 前端更新界面 → 弹窗按编排顺序弹出
```

**为什么分前后端？** 游戏真相（谁是狼人）必须藏在后端——前端代码用户按 F12 就能看到。所以你会看到 `snapshot()` 函数专门做『防剧透过滤』：发给前端的玩家数据只有 `id/name/alive`，绝不含 `role`。

```js
// server/modes/deduction.js · snapshotDeduction()
players: w.players.map((p) => ({ id: p.id, name: p.name, alive: p.alive })),
// 注意：没有 role / cover 字段——这就是防剧透
roles: over ? w.players.map(...) : null,   // 身份表仅终局下发
nightLogs: over ? (w.nightLogs || []) : null, // 夜间日志同样仅终局
```

### 🔍 深挖问答

**Q：fetch POST 是什么？和浏览器地址栏输入网址有什么区别？**

浏览器地址栏输入网址是 **GET 请求**——『我要看这个页面』，只有地址没有内容。`fetch` 是 JS 发起网络请求的内置函数，POST 是它的另一种方式——『我要提交数据』，请求里带着 `body`（比如 `{ type: 'adjudicate', targetId: 'p3' }`）。点击按钮触发的是 POST，因为你在告诉服务器『我要做这个动作』，而不只是看页面。

**Q：JSON 是什么？**

JSON（JavaScript Object Notation）是一种**文本格式**，用来在网络上传输结构化数据。它长得像 JS 对象：`{"name": "陆离", "alive": false}`。前后端之间传的都是 JSON——发送前 `JSON.stringify(对象)` 把对象变成文本，收到后 `JSON.parse(文本)` 还原成对象。为什么用文本？因为网络只能传字节流，文本是最通用的『包装』。

**Q：前端代码用户能看到，后端代码呢？**

看不到。前端代码（编译后的 JS）必须下载到浏览器才能运行，所以用户 F12 就能读；后端代码只活在服务器上，用户只能通过 API 拿到**后端选择返回的数据**。这就是为什么『谁是狼人』必须只存在于后端——前端哪怕一个字都不写，只要 API 不返回，用户就看不到。

**Q：生产模式下 Caddy 和 Express 到底是什么关系？各管什么？**

两层分工，像『前台接待』和『后厨』：

```
用户浏览器 --HTTPS(443)--> Caddy（前台） --HTTP--> Express(localhost:3001)（后厨）
```

| | Caddy（反向代理层） | Express（应用层） |
|---|---|---|
| 职责 | 面向公网的『大门』：TLS 加密/HTTPS 证书（自动申请续期）、监听 80/443、**传输压缩**（encode gzip/zstd）、将来还可加限流/缓存 | 游戏逻辑：API 路由、口令与登录校验、AI 调用、SQLite 存档、静态文件托管 |
| 暴露给公网？ | 是（防火墙只开 22/80/443） | 否——只听 localhost:3001，公网摸不到 |
| 挂了会怎样 | 全站不可达（大门关了） | 同样全站不可达（后厨停了），但 Caddy 会返回 502 类错误页 |

**为什么不让 Express 直接面向公网？** ① TLS 证书管理麻烦（Caddy 自动搞定，含自签/域名证书）；② 职责分离——加密/压缩这类『通用脏活』交给专门的网关层，应用层专注业务；③ 安全——3001 不暴露，攻击面更小。

**Q：开启压缩会不会影响服务器性能？**

压缩的代价是 **CPU 换带宽**：压缩 160KB 的 JS 约消耗几毫秒 CPU。对本项目的规模（个人游戏站、并发个位数），这点开销完全可以忽略——服务器当前 CPU 占用仅 1% 左右，余量巨大。而且换来的是传输量降 63%，用户加载更快、流量包消耗更少，**净收益为正**。

什么情况下压缩才需要斟酌：高并发大流量站点（每秒成百上千次请求）CPU 成本会累积——那种场景用预压缩（构建时生成 .gz 文件，Caddy 直接发送不再现场压缩）或 CDN 解决。本项目远达不到这个量级。

**Q：Caddy 压缩后，Express 需要解压吗？**

不需要——**压缩只发生在 Caddy → 浏览器这一段**，完整链路是：

```
Express(3001) --未压缩的原始数据--> Caddy --现场压缩--> 浏览器 --自动解压--> 渲染页面
```

Express 发给 Caddy 的永远是原始数据（它根本不知道 Caddy 压缩了）；Caddy 在转发响应的路上现场压缩，并在响应头加 `Content-Encoding: gzip` 标记；浏览器看到这个标记就自动解压——**解压是浏览器的职责**，不是 Express 的。Express 全程无感知，一行代码不用改。

这也是『反向代理』的含义：对浏览器来说 Caddy 就是服务器；对 Express 来说 Caddy 只是本机的一个内部客户。压缩是 Caddy 在中间做的『加工』，两端都不知道对方的存在。

**Q：为什么需要 Express？只用 Caddy 行不行（不改代码）？**

不行——因为 **Caddy 不会『跑程序』，只会『发文件』**。两者的本质区别：

| | Caddy | Express |
|---|---|---|
| 本质 | Web 服务器：接收请求 → 返回**现成的文件**或转发给别的程序 | 应用服务器：接收请求 → **执行代码**（跑 JS 逻辑）→ 动态生成响应 |
| 能做什么 | 发静态文件、TLS 加密、压缩、反向代理 | 一切业务逻辑：API 路由、口令/登录校验、调 AI、读写 SQLite、结算游戏 |
| 不能做什么 | 执行应用代码——它没有『运行 JavaScript 游戏逻辑』的能力 | （相对）面向公网的高效大门（TLS/压缩这些通用活它不如 Caddy 专业） |

本站的内容分两类：静态文件（HTML/JS/CSS，现成的）和动态 API（/api 的每个响应都要**现场计算**——查存档、调 AI、结算夜晚）。Caddy 能独立搞定前者，但后者必须有个程序去执行 `server/` 里的代码——这个程序就是 Express（Node.js 进程）。

**类比**：Caddy 是前台，能递上印好的菜单；但菜要现炒——后厨（Express）必须存在。撤掉后厨，前台只能发菜单，没人做菜。

**『不改代码』的前提下结论明确**：代码就是 Express 应用——去掉 Express 等于去掉整个游戏，Caddy 独立只能撑起一个纯静态网站（没有登录、没有存档、没有 AI）。

**顺带**：Caddy 其实可以接管『发静态文件』这份活（`file_server` 指令），让 Express 专心做 API——但这是分工微调，不是替代，Express 依然必须在。

**Q：当前 Caddy 和 Express 的实际分工是什么？是『Caddy 发静态文件、Express 做 API』吗？**

**不是——当前是『Caddy 全转发、Express 全包』**。看 Caddyfile 的真实配置：

```
124.220.208.156 {
	encode zstd gzip
	reverse_proxy localhost:3001   # 所有请求（页面 + /api）统一转给 Express
}
```

没有 `file_server` 指令——意味着浏览器请求 JS/CSS 时，流程是：Caddy 收到 → 转给 Express → Express 的 `express.static` 从 dist/ 读文件发回 → Caddy 压缩后转给浏览器。**静态文件也走了 Express 一道**。

两种分工对比：

| | 当前方案（全转发） | file_server 方案（静态走 Caddy） |
|---|---|---|
| 静态文件路径 | 浏览器 → Caddy → **Express** → Caddy → 浏览器 | 浏览器 → **Caddy 直接发**（不经过 Express） |
| API 路径 | 浏览器 → Caddy → Express | 同左 |
| Express 负担 | 静态 + API 都管 | 只管 API |
| 优点 | 单端口同源、配置最简、行为完全一致 | 静态请求不占用 Node 进程，高并发下更省 |
| 缺点 | 每个静态请求都过一道 Node（本项目量级无感） | Caddyfile 要多几行配置，需处理路径映射 |

**对本项目的量级（并发个位数），两种方案性能差异可以忽略**——当前方案胜在简单。等流量大了再切换也只是一次配置改动。

**Q：将来买了域名，Caddy 那边是不是改一个配置就行？**

是的——这正是当初选 Caddy 的主要原因。当前配置用自签证书（浏览器首次访问需手动信任），切换到域名只需三步：

```
① 域名 DNS 解析：把域名 A 记录指向服务器公网 IP
② 改 Caddyfile：把站点块的 IP 换成域名（可删掉 default_sni 全局块）
③ systemctl reload caddy
```

改完后 Caddy 会自动向 Let's Encrypt 申请**受信任证书**（免费、自动续期），浏览器不再弹安全警告。前端代码**一行不用改**——API 用的都是相对路径（/api/...），换域名自动跟随。

**为什么这么简单？** Caddy 内置了证书自动化（ACME 协议）：它发现站点块写的是域名而非 IP，就会自动走申请流程——验证域名归属（通过 80 端口）→ 拿到证书 → 到期前自动续期。Nginx 等传统服务器要手动用 certbot 申请、配置、设续期任务，Caddy 把这些全包了。

**一个注意点**：切换后旧的自签证书访问方式（直接用 IP 访问）将不再匹配站点块——如果还想保留 IP 访问，可以两个站点块并存（IP 一个、域名一个）。

**Q：后端怎么同时提供页面和 API？静态托管是什么？**

`server/index.js` 里有这两行：

```js
app.use('/api', apiRouter);              // /api 开头的请求 → 走游戏逻辑
app.use(express.static(dist));           // 其余请求 → 直接返回 frontend/dist 里的文件
```

`express.static` 是静态文件托管——把一个文件夹『暴露』成可访问的 URL：请求 `/` 就返回 `dist/index.html`，请求 `/assets/index-xxx.js` 就返回对应 JS 文件。所以一个端口（3001）同时干两件事：API 走逻辑、其他走文件。这也是为什么改前端代码后要 `npm run build`——构建产物在 `dist/` 里，后端托管的是它，不是源码。

**Q：中间件（middleware）是什么？**

Express 的请求处理像流水线：请求进来依次经过一串函数，每个函数可以『处理一下然后放行』或『直接拦截返回』。`app.use(x)` 就是往流水线上加一个工位。本项目流水线上的工位依次是：口令校验（AccessGate）→ JSON 解析（把请求体变成 req.body）→ 各 API 路由 → 静态文件。理解流水线就能定位『请求卡在哪一步了』。

## 第 2 课：前端——Vue 组件如何工作

### 2.1 组件 = HTML + 逻辑 + 样式三合一

每个 `.vue` 文件分三块：

```vue
<script setup>            // ① 逻辑：变量、函数
const showSaves = ref(false);   // ref() 创建响应式变量
</script>

<template>                // ② 结构：变量变了界面自动变
  <div v-if="showSaves">存档浮层</div>  <!-- v-if 控制显示 -->
</template>

<style scoped>            // ③ 样式：scoped 表示只作用于本组件
.save-overlay { position: fixed; inset: 0; }
</style>
```

**核心心智模型**：`ref(false)` 是一个『被监控的盒子』。改它的值（`showSaves.value = true`），所有用到它的模板位置自动更新——不需要你手动操作 DOM。

### 2.2 组件间通信：inject

推理杀界面不自己管理游戏状态，而是从父级『注入』：

```js
// DeductionView.vue 第 6 行
const { state, listenSpeeches, adjudicateTarget, backToHome, restart } = inject('game');
```

`state` 是全局游戏状态（当前对局、历史消息、加载中……），`listenSpeeches` 等是操作函数。它们定义在 `frontend/src/composables/useGame.js`，由 `App.vue` 通过 `provide('game', game)` 提供给所有子组件。

### 2.3 弹窗时序是怎么实现的（本项目最精巧的前端逻辑）

问题：处刑后服务端**一次性**返回处刑结果 + 新一夜信息，两个弹窗的监听器同帧触发，谁先谁后不可控。

解法：**暂存队列**。看 `DeductionView.vue` 中的关键代码：

```js
let pendingNightEvent = null;   // 暂存的夜间事件
let pendingEndModal = false;    // 暂存的终局结算

// 夜间事件监听：处刑结果弹窗还开着 → 先存着，别弹
watch(() => [d.value.round, d.value.phase, state.gameOver], () => {
  const evt = { round: r, deaths: ..., peaceful: ... };
  if (execResult.value) pendingNightEvent = evt;  // 关键：暂存
  else nightEvent.value = evt;                    // 否则直接弹
});

// 处刑结果弹窗关闭（execResult 变 null）→ 释放暂存的弹窗
watch(execResult, (v) => {
  if (!v) {
    if (pendingNightEvent) { nightEvent.value = pendingNightEvent; pendingNightEvent = null; }
    if (pendingEndModal)  { showEndModal.value = true;  pendingEndModal = false; }
  }
});
```

**逐行解释**：`watch(execResult, ...)` 监视处刑结果弹窗的数据——当它从有值变为 `null`（用户点了『知道了』），依次把暂存的夜间事件、终局结算放出来。这就保证了『处刑结果 → 夜间事件 → 终局结算』的顺序。

### 2.4 收回动画的原理

弹窗关闭时如果直接 `v-if=false`，元素瞬间消失。本项目用 Vue 的 `<Transition>` 包装：

```vue
<Transition name="ovl">
  <div v-if="execResult" class="review-overlay">...</div>
</Transition>
```

Vue 会在元素**移除前**先加上 `ovl-leave-active` class，等 CSS 过渡播完才真正移除 DOM：

```css
.ovl-leave-active .review-modal {
  transition: transform 0.22s ease, opacity 0.22s ease;
  transform: scale(0.85) translateY(14px);  /* 缩小下沉 */
  opacity: 0;
}
```

### 🔍 深挖问答

**Q：为什么 script 里写 `showSaves.value = true`，模板里却直接写 `showSaves` 不带 .value？**

`ref()` 返回的是一个『包装对象』（`{ value: false }`），JS 里必须通过 `.value` 读写。但模板是 Vue 编译器处理的——它看到裸的 `showSaves` 会自动帮你加 `.value`。这是 Vue 的语法糖：模板里省心，script 里要记得加（初学者最常犯的错就是 script 里忘了 `.value`）。

**Q：watch 是什么？它是怎么『监视』的？**

`watch(数据, 回调)` = 『当这个数据变化时，执行回调』。原理：Vue 修改响应式数据时会触发一个通知机制，所有 watch 过这个数据的地方都会被调用。第一个参数传函数（如 `() => [d.value.round, ...]`）时，Vue 会记录函数里**读取过**的所有数据，任何一个变了就触发——这叫依赖收集。`{ immediate: true }` 表示『注册时立刻先执行一次回调』，用于初始化（比如页面刚加载就要判断当前该不该弹窗）。

**Q：provide/inject 和 props 传值有什么区别？什么时候用哪个？**

props 是**父子直传**：父组件模板里 `<Child :name="x" />`，一层层传。层级深了会变成『props 钻井』——中间组件明明不用这个数据也得帮忙传。provide/inject 是**跨层级注入**：App.vue `provide('game', game)` 后，**任意深度**的子孙组件都能 `inject('game')` 拿到。适合全局性的东西（用户信息、游戏状态）。本项目游戏状态所有视图都要用，所以选 inject。

**Q：scoped 样式是怎么做到『只作用于本组件』的？**

编译时 Vue 给本组件每个元素加一个随机属性（如 `data-v-7ba5bd90`），并把 CSS 选择器改写成 `.save-overlay[data-v-7ba5bd90]`。别的组件即使有同名 class，因为没有这个属性也匹配不上。这是编译期技巧，不是运行时隔离。

## 第 3 课：后端——路由与游戏引擎

### 3.1 路由：URL 到函数的映射

`server/index.js` 用 Express 注册路由：

```js
app.post('/api/game/:id/action', async (req, res) => { ... });
//        └─ 路径参数 :id 会出现在 req.params.id
```

前端调用（`frontend/src/api.js`）：

```js
adjudicate: (gameId, targetId) =>
  request(`/api/game/${gameId}/action`, {
    method: 'POST',
    body: JSON.stringify({ type: 'adjudicate', targetId }),
  })
```

### 3.2 可插拔模式：新增玩法不改路由

所有模式注册在 `server/modes/index.js` 的表里，路由按 `mode` 字段分发：

```js
const MODES = { world: {...}, detective: {...}, wolf: {...}, deduction: {...} };
// 每个模式实现统一接口：newGame / handleAction / snapshot ...
```

这就是『可插拔』的含义：写一个新模式文件、注册进表里，路由层零改动。

### 3.3 推理杀引擎的确定性结算

夜晚逻辑**不走 AI**——狼刀谁、守卫挡没挡住，全部由代码计算（`settleNight` 函数，约 300 行）。AI 只负责把结算结果『演』成角色发言。为什么？因为 AI 会算错，代码不会。

```js
// 简化的结算顺序（实际有 9 个阶段）
processTurn(w);          // 阶段 0：变身判定
const A = lockActions(w); // 阶段 1：锁定本夜行动（谁对谁做什么）
executeNightActions(w, A, ...); // 阶段 2~9：结算效果、落盘死亡
```

### 🔍 深挖问答

**Q：Express 到底是什么？app.post 这行代码每个部分是什么意思？**

Express 是 Node.js 最流行的 Web 框架——它帮你把『监听端口、解析 HTTP 请求、分发到处理函数』这些脏活包了，你只需要声明『什么路径交给什么函数』。拆解这行：

```js
app.post('/api/game/:id/action', handler)
// │    │     │                │         └─ 处理函数（收到匹配请求时执行）
// │    │     │                └─ 路径模式：:id 是占位符，匹配任意值
// │    │     └─ URL 路径
// │    └─ HTTP 方法（还有 app.get / app.put 等）
// └─ Express 应用实例
```

**Q：req 和 res 是什么？**

每个请求进来，Express 会构造两个对象传给你的处理函数：`req`（request）装着请求的一切——URL 参数（`req.params.id`）、请求体（`req.body`）、请求头；`res`（response）是你回信的工具——`res.json(数据)` 把对象变成 JSON 发回去并结束响应。一个进一个出。

**Q：路径参数 :id 是怎么工作的？**

注册 `/api/game/:id/action` 后，Express 把 `:id` 位置的内容捕获进 `req.params`。请求 `/api/game/mv62suww/action` → `req.params.id === 'mv62suww'`。这样一条路由就能处理所有游戏，不用为每个存档写一条。

**Q：async 是什么意思？**

标记函数为异步——函数内可以用 `await`（等待耗时操作完成，如调 AI、查数据库），期间不阻塞服务器处理其他请求。没有 await 的话，10 个用户同时玩，第 2 个要等第 1 个的 AI 调用完才能动。

## 第 4 课：AI 调用——提示词与输出约束

### 4.1 一次调用的样子

`server/llm.js` 封装了 OpenAI 兼容接口（零 SDK，原生 fetch）：

```js
async function chat(messages, opts = {}) {
  const res = await fetch(`${BASE_URL}/chat/completions`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${API_KEY}` },
    body: JSON.stringify({ model: MODEL, messages, ...opts }),
  });
  // 返回 JSON：choices[0].message.content 是 AI 的回复文本
}
```

`messages` 是对话数组：`system`（设定/规则）+ `user`（本次指令）。

### 4.2 为什么 AI 输出需要『五层防护』

AI 偶尔不按格式回复（漏 JSON 括号、输出敷衍短句、坏人自曝身份）。项目在 `generateSpeech` 里逐项校验：

```js
let speech = String((obj && obj.speech) || '').trim().slice(0, MAX_SPEECH);

// 校验 1：过短 → 用知识包兜底
if (speech.length < 24) speech = fallbackSpeech(game, speaker);

// 校验 2：坏人自曝（『我是狼人』）→ 兜底为伪装话术
if (EVIL_ROLES.includes(speaker.role)) {
  if (new RegExp(`我是${ROLES[speaker.role]}`).test(speech))
    speech = fallbackSpeech(game, speaker);
}

// 校验 3：紧邻重复短语折叠（LLM 偶发『有些异常动静，有些异常动静』）
speech = speech.replace(/([^，。！？、；\s]{4,16})[，、；\s]+\1/g, '$1');
```

**设计思想**：AI 负责『措辞』，代码负责『事实』。事实错了游戏就崩了，所以一切关键信息都由程序生成或校验。

### 🔍 深挖问答

**Q：system 消息和 user 消息有什么区别？**

`system` 是给 AI 的『人设与规则』——『你是推理杀玩家陆离，必须按以下事实发言……』，权重高、贯穿全程；`user` 是本次的具体指令——『请发表你的发言』。类比：system 是员工手册，user 是今天的工作单。本项目把角色知识包全放 system，保证 AI 不会跑偏。

**Q：temperature 是什么？为什么发言用 0.8？**

控制随机性的参数（0~2）：越低越确定（每次问都给差不多的答案），越高越发散。0.8 偏高，因为游戏发言需要多样性——十个角色每次说一样的话很无聊。但事实类输出（如世界观解析）会用低温度，因为要稳定。

**Q：为什么让 AI 按 JSON 格式回复？**

AI 默认输出一段自然语言，程序没法直接用。约定输出 `{"speech": "...", "suspect": "..."}` 这样的 JSON，程序 `JSON.parse` 后就能精确取字段。代价是 AI 偶尔格式写错（漏括号、加解释文字），所以需要容错解析和重试——这就是五层防护存在的原因。

**Q：API Key 是什么？为什么放在 .env 而不是代码里？**

API Key 是你向 AI 服务商（OpenAI 或兼容平台）申请的『钥匙』——请求时放在 Authorization 头里证明『这个调用记在我账上』（AI 调用按 token 计费，谁出钱谁给钥匙）。放代码里的问题：代码要提交 git 推到 GitHub，密钥就公开了，任何人都能拿你的钥匙刷你的账单。`.env` 被 .gitignore 排除，永远不进仓库；代码通过 `process.env.LLM_API_KEY` 读取——Node 启动时会把 `.env` 文件的内容装进这个环境变量对象。

**Q：环境变量（process.env）是什么？**

操作系统给每个进程的『配置便签』——一组键值对，进程运行时随时能读。好处：同一份代码不改一行，换台机器换个 `.env` 就能用不同的密钥/端口。`PORT=3001` 也是这么读的（`process.env.PORT || 3001`：有配置用配置，没有用默认值）。

**Q：校验 3 那行正则每个符号是什么意思？**

逐段拆解 `/([^，。！？、；\s]{4,16})[，、；\s]+\1/g`：

| 片段 | 含义 |
|------|------|
| `( ... )` | 捕获组——把匹配到的内容『记住』，供后面引用 |
| `[^，。！？、；\s]` | 一个**不是**标点/空白 的字符（`^` 在方括号内表示取反） |
| `{4,16}` | 前面的字符重复 4~16 次——即一个 4~16 字的短语 |
| `[，、；\s]+` | 一个或多个标点/空白（短语之间的间隔） |
| `\1` | **反向引用**——要求和第 1 个捕获组**一模一样的内容**（同一个短语再说一遍） |
| `g` | 全局标志——替换所有匹配，不只第一个 |

整体含义：『找一个 4~16 字的短语，后面跟着标点，然后同一个短语又出现』——即紧邻重复。替换成 `$1`（只保留第一遍）。所以『有些异常动静，有些异常动静』变成『有些异常动静』。

## 第 5 课：数据存储——SQLite 存档

### 5.1 两张表

`data/game.db`（better-sqlite3 驱动，同步 API 无回调地狱）。**逐字段说明**：

**users 表（账号，一人一行）**

| 字段 | 类型 | 含义 | 例子 |
|------|------|------|------|
| `id` | TEXT 主键 | 用户唯一标识，注册时生成：`'u_' + 16 位随机十六进制` | `u_03e568465c1e5b3f` |
| `username` | TEXT 唯一 | 用户名（明文——它本来就要显示，无需保密） | `陆离` |
| `password_hash` | TEXT | 密码的『盐:哈希』（见 5.5 节，**不是密码本身**） | `a3f8...:b1c9...` |
| `created_at` | INTEGER | 注册时间戳（毫秒数，`Date.now()` 的值） | `1791859365248` |

**saves 表（存档，一局游戏一行）**

| 字段 | 类型 | 含义 | 例子 |
|------|------|------|------|
| `id` | TEXT 主键 | 存档唯一标识，开局时生成：时间戳36进制 + 随机串 | `mv62suww-rrps` |
| `user_id` | TEXT | **谁的存档**——指向 users.id，相当于外键 | `u_03e568465c1e5b3f` |
| `mode` | TEXT | 游戏模式（world/detective/wolf/deduction） | `deduction` |
| `data` | TEXT | **整个游戏对象的 JSON 序列化**（见下） | `{"deduction":{...},...}` |
| `created_at` | INTEGER | 开档时间戳（毫秒） | `1791859140188` |
| `updated_at` | INTEGER | 最后游玩时间戳（毫秒），每次存档都刷新 | `1791859279219` |

两表的关系：`saves.user_id` → `users.id`。查『某用户的所有存档』= `SELECT * FROM saves WHERE user_id = ?`，按 `updated_at` 倒序就是『最近游玩在前』的存档列表。

`data` 列存的是**整个游戏对象的 JSON 序列化**——玩家、历史消息、夜晚状态全在里面。读档 = `JSON.parse(row.data)`。

**为什么时间存毫秒数字而不是『2026-10-13』这种字符串？** 毫秒数（Unix 时间戳）是数字，比较大小就是比较先后，排序/过滤直接用；格式化成人类可读形式是**显示时**才做的事（前端 `new Date(s.updatedAt).toLocaleString()`）。存原始值、显示时再格式化，是时间存储的标准做法。

**为什么 id 不用 1、2、3 自增？** 随机 id 不泄露业务信息（看不出来有多少用户/存档），且天然无冲突地能跨库合并。自增 id 还容易被遍历（/api/save/1、/api/save/2……挨个试）。

### 5.2 查看存档内容（调试常用）

```js
// /tmp/query.js
const db = require('/项目路径/server/node_modules/better-sqlite3')('/项目路径/data/game.db');
const saves = db.prepare('SELECT id, mode, updated_at FROM saves ORDER BY updated_at DESC LIMIT 5').all();
```

运行：`node /tmp/query.js`。**作用**：直接检查存档数据排查游戏逻辑问题（比如某角色发言异常时，看它的 `role` 和知识包）。

### 5.3 预编译语句与 SQL 注入（重要）

项目里所有数据库操作都是这个模式：

```js
db.prepare('SELECT data FROM saves WHERE id = ?').get(id);
//           └──────── SQL 模板（带 ? 占位符） ────────┘      └ 参数
```

**为什么这样写而不是直接拼字符串？** 假设你拼字符串：

```js
// ❌ 危险的反面教材（项目里没有这种代码）
db.prepare(`SELECT * FROM users WHERE username = '${name}'`).get();
```

如果用户注册时输入的用户名是 `x' OR '1'='1`，拼出来的 SQL 变成：

```sql
SELECT * FROM users WHERE username = 'x' OR '1'='1'
--                                      └─ 恒为真！条件失效，返回全部用户
```

这就是 **SQL 注入**——用户输入被当成了 SQL 代码的一部分执行。更狠的输入甚至能删表。

**占位符机制为什么能防住？** 关键在于**解析和传值是两个分离的阶段**：

1. `db.prepare(sql)` 阶段：数据库引擎先把 SQL 模板**解析成语法树**——此时 `?` 被标记为『这里将来会有一个值』，模板的结构（哪是命令、哪是数据位）已经**固定死**；
2. `.run(id)` / `.get(id)` 阶段：参数作为**纯数据**填进占位符——引擎对参数不做任何解析，哪怕参数里有 `'`、`OR`、分号，也只是一个普通字符串值，永远不会被当成 SQL 命令。

一句话：**拼字符串时『代码和数据混在一条文本里』，注入就有机可乘；预编译时『代码结构先定死，数据后填入』，数据永远只是数据**。

**『预编译』的另一半好处**：同一条 SQL 反复执行时（比如每回合都存档），解析只发生一次，后续执行直接复用语法树——更快。这就是 `prepare`（准备）这个名字的含义。

### 5.4 WAL 模式是什么

```js
db.pragma('journal_mode = WAL');  // storage.js 初始化时设置
```

数据库写入时最怕『写一半断电，文件损坏』。默认模式下，写入要锁住整个文件，读写互相排队。**WAL**（Write-Ahead Logging，预写日志）把改动先写进旁边的 `-wal` 文件，攒多了再合并回主文件——写入期间主文件照常可读，读写不再互相阻塞。

**实用提醒**：正因为最新数据可能还在 `-wal` 里，**直接拷贝 `game.db` 单个文件做备份会丢数据**，要连 `game.db-wal`、`game.db-shm` 一起拷（或先让程序正常关闭）。

### 5.5 密码为什么存 hash 而不是明文

```js
// 注册时
const salt = crypto.randomBytes(16).toString('hex');          // 随机盐
const hash = crypto.scryptSync(password, salt, 64).toString('hex');
return `${salt}:${hash}`;   // 存的是『盐:哈希』，不是密码本身

// 登录时
const check = crypto.scryptSync(password, salt, 64).toString('hex');
return crypto.timingSafeEqual(Buffer.from(hash), Buffer.from(check));
```

**哈希**是单向函数：密码 → 哈希容易，哈希 → 密码（实际上）不可能。数据库被拖走，攻击者拿到的也只是哈希，反推不出密码。**盐**（salt）是每个用户随机的 16 字节——防止攻击者用『常见密码哈希对照表』批量碰撞（没有盐时 `123456` 的哈希全网一样，一查便知；有盐后每人不同）。**scrypt** 是一种故意设计得『慢且吃内存』的哈希算法，让暴力穷举的成本极高。`timingSafeEqual` 用恒定时间比较，防止攻击者通过响应快慢逐位猜哈希。

### 5.6 账号体系全流程：用户名和密码到底是怎么存的

先给结论：**用户名明文存，密码永远不存明文——只存『盐 + 哈希』**。整个流程分注册、登录、后续请求三段。

**① 注册（POST /api/auth/register）**

```
用户提交 username / password
   │
   ├─ 校验：用户名 2~16 位（字母/数字/下划线/中文）、密码 6~64 位
   ├─ 查重：findUserByName —— 重名直接拒绝
   ▼
storage.createUser(username, password)
   │
   ├─ 生成随机 id：'u_' + 16 位随机十六进制
   ├─ 密码哈希（见 5.5 节）：scrypt(密码, 随机盐) → '盐:哈希'
   ▼
INSERT INTO users (id, username, password_hash, created_at)
```

数据库里实际存的一行长这样（示意）：

```
id: u_03e568465c1e5b3f
username: 陆离            ← 明文（用户名本来就要显示，无需保密）
password_hash: a3f8...e2:b1c9...77   ← 盐:哈希，反推不出密码
```

**② 登录（POST /api/auth/login）**

```
用户提交 username / password
   │
   ├─ 防爆破：该用户名已连续失败 5 次？→ 锁定 10 分钟
   ├─ 查库取出该用户的 盐:哈希
   ├─ 用同样的盐对提交的密码做 scrypt → 得到候选哈希
   ├─ 恒定时间比较两个哈希（timingSafeEqual）
   │     ├─ 不一致 → 记一次失败，返回『用户名或密码错误』
   │     └─ 一致 → 清空失败计数，签发 JWT 令牌
   ▼
返回 { token, user } → 前端把 token 存进 localStorage
```

注意错误文案是**『用户名或密码错误』**——故意不区分是哪个错了。如果分开提示，攻击者可以先试用户名枚举出哪些账号存在。

**③ 后续每次请求：JWT 令牌怎么证明『我是我』**

登录后前端每个请求都带上令牌：

```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOiJ1XzAz...eyJzaWc...
```

这个长字符串是 **JWT**（JSON Web Token），由三段用点连接：

```
头部.载荷.签名
  │     │     └─ HMAC-SHA256(头部.载荷, 服务器密钥) —— 只有服务器能算出
  │     └─ JSON：{ uid, username, iat(签发时间), exp(72小时后过期) }
  └─ JSON：{ alg: 'HS256', typ: 'JWT' }
```

服务器收到令牌后做的事（`verifyToken`）：

1. 按点拆成三段；
2. **用自己手里的密钥重新计算一遍签名**，和令牌第三段恒定时间比较——对不上就是伪造（攻击者没有密钥，改了载荷也算不出正确签名）；
3. 解析载荷，检查 `exp` 是否过期；
4. 全过 → 从载荷取出 `uid`，这就是当前用户。

**关键点**：令牌本身**不含密码**，也不需要服务器存它——验证靠的是『密钥 + 签名算法』的数学关系，服务器是无状态的（重启不丢登录态）。签名密钥 `JWT_SECRET` 存在 `.env` 里，首次启动自动生成。

### 5.7 存档在哪里、怎么和用户对应、有加密吗

**存档位置**：`data/game.db` 的 `saves` 表，每局游戏一行。

**和用户的对应关系**：靠 `saves.user_id` 列——存档创建时写入当时登录用户的 id，相当于外键关联 `users.id`：

```sql
saves (id, user_id, mode, data, ...)
          └─ 谁的存档，指向 users.id
```

**每次访问存档都校验归属**（`server/index.js` 的 `findGame`）：

```js
const owner = storage.getSaveOwner(req.params.id);
if (owner && owner !== user.id) {
  res.status(404).json({ error: '存档不存在' });  // 他人存档按不存在处理
  return null;
}
```

注意这里返回 **404 而不是 403**——403（无权限）等于告诉攻击者『这个存档存在，只是不是你的』；404 则连存在性都不暴露。存档列表接口也只查当前用户的：`WHERE user_id = ?`，所以每个账号只能看到自己的存档（上限 20 个）。

**存档有加密吗？没有。** `data` 列是明文 JSON。为什么可以接受：

- 存档的威胁模型是『其他玩家偷看』——这靠归属校验（上面的 404 机制）挡住，不需要加密；
- 能直接读数据库文件的只有**服务器管理员**（也就是你自己）——对管理员加密没有意义，密钥总得存在服务器上；
- 加密反而带来成本：密钥管理、调试时查不了存档（第 5.2 节的排查手段会失效）。

真正需要保密的东西都另有安排：密码存哈希（5.5 节）、API 密钥在 `.env`（不进 git）、JWT 签名密钥同样在 `.env`。

### 🔍 深挖问答

**Q：这个『令牌』是 access token 吗？和 .env 里的 ACCESS_TOKEN 是一回事吗？**

是 access token，但和 ACCESS_TOKEN **完全是两个东西**，只是名字撞了：

| | JWT 令牌 | ACCESS_TOKEN（访问口令） |
|---|---|---|
| 是什么 | 登录后服务器签发的**身份凭证**（5.6 节讲的就是它） | `.env` 里配置的**整站密码** |
| 谁定的 | 服务器动态生成（每人每次登录一个） | 你自己手动配置 |
| 证明什么 | 『我是用户 xxx』 | 『我可以进入这个网站』 |
| 放哪里 | 浏览器 localStorage，随请求头发送 | 用户首次访问时在口令页输入 |
| 有效期 | 72 小时自动过期 | 前端 7 天免输，后端永久有效 |

**access token 是什么**：身份认证领域的通用术语——『访问凭证』。登录成功后服务器发给你，之后每个请求都带着它，服务器看它就知道你是谁、不用每次重新输密码。JWT 是它的一种**实现格式**（三段点分字符串）；别的方式还有不透明随机串（服务器查库存档对号）。所以关系是：**access token 是概念，JWT 是实现**——本项目的 access token 用 JWT 格式实现。

顺带一提术语表里还有个常见词 **refresh token**（刷新令牌）：access token 短期有效、refresh token 长期有效，前者过期后用后者换新的，避免频繁登录。本项目没做这套——72 小时后直接重新登录，对游戏网站够用。

**Q：口令 7 天过期了，但我的登录（JWT 72 小时）还没过期，会绕过口令直接访问吗？**

不会。这两道门是**串联**的，每个请求都要依次过：

```
每个 /api 请求
  → 第 1 道门：口令中间件——检查请求头 X-Access-Token 是否正确，不对就 401
  → 第 2 道门：JWT 校验——检查 Authorization 头的令牌是否有效，无效就 401
  → 两道都过 → 才执行游戏逻辑
```

关键在『**每个请求**』：口令不是『进站时查一次票』，而是『每一站都查票』。口令过期（前端 7 天后自动清除、不再携带）→ 下一个请求在**第 1 道门**就被 401，根本走不到 JWT 那一步。JWT 再有效也没用——这就是串联（AND）关系：任何一道不过，整体拒绝。此时前端会重新弹出 AccessGate 口令页，输对口令后继续，**登录态（JWT）不受影响**，不用重新登录。

一个细节：『7 天过期』是**前端**行为——localStorage 里的口令记录带保存时间，超时自动清除。后端本身不跟踪口令有效期，只要请求头带上正确口令就放行。所以真正的失效手段是改 `.env` 里的 ACCESS_TOKEN 并重启——旧口令立刻全部失效。

**Q：两道门完整数据流——各存在哪、用户输入去哪、怎么校验、时间怎么判？**

一张表看全（这是前面几问的汇总地图）：

| | 访问口令 | 登录令牌（JWT） |
|---|---|---|
| 服务器存什么 | 存**正确口令本身**（`.env` 的 ACCESS_TOKEN，验证 = 比对） | 只存**签名密钥** JWT_SECRET，**不存任何令牌**（验证 = 重算签名比对） |

> ⚠️ 注意区分：口令的验证是『对答案』——服务器存着正确答案，拿来比；JWT 的验证**没有『正确答案』存在服务器**——令牌是每次登录动态生成的、谁都不存它，服务器只存签名密钥，靠『用密钥重算签名是否一致』来验证。所以 JWT_SECRET 不是令牌的答案，是**造签名的钥匙**。
| 用户输入什么 | AccessGate 页输入口令 | 登录页输入用户名+密码 |
| 输入后去哪 | 存浏览器 localStorage（`rpg_access_token`，带保存时间） | 密码发给后端验证后**即弃不存**；返回的 JWT 存 localStorage（`rpg_auth_token`） |
| 请求时怎么带 | 每个请求加头 `X-Access-Token: 口令` | 每个请求加头 `Authorization: Bearer 令牌` |
| 后端怎么验正确性 | 中间件取出请求头，与内存里的口令**直接字符串比较**，不等就 401 | 用 JWT_SECRET **重算一遍签名**，与令牌第三段**恒定时间比较**，不符即 401 |
| 时间怎么判 | **后端不判**——口令永不过期；过期是前端行为：读 localStorage 时查 `now - savedAt > 7天` → 超时自动清除 → 请求不带口令 → 后端 401 | **后端判**——令牌载荷里自带 `exp`（签发时算好的过期时间戳），验证时查 `exp < now` → 过期即 401 |
| 服务器要不要存它 | 不存（配置即答案） | 不存（无状态——签名数学关系即证明，重启不丢登录态） |

**两个时间校验的本质区别**：口令的过期判断在**前端**（localStorage 记录带 savedAt，读时自查）——所以后端无法主动让某个设备的口令提前失效，只能改 `.env` 换新口令让全部失效；JWT 的过期判断在**后端**（exp 写死在令牌里）——所以令牌一旦签发，72 小时内天然有效，服务器无法提前作废单个令牌（这也是 refresh token 机制要解决的问题）。

**密码输入后去哪了**：登录请求的 body 里 → 后端 `verifyPassword` 用库里的盐对它重算 scrypt → 与库中哈希恒定时间比较 → 比完即弃，**全程不存储明文**。数据库里永远只有『盐:哈希』。

**Q：如果服务器整个被攻破了，密钥不就全被拿走了？用户数据不就泄密了？**

是的——**服务器被完全攻破 = 一切皆失**。这是所有安全设计的边界事实，要先接受它再谈防护。攻击者拿到服务器权限后能拿到：JWT_SECRET（可伪造任意用户令牌）、ACCESS_TOKEN（可进入站点）、整个数据库（存档明文、密码哈希）。

**那为什么还要做这些防护？** 因为各层防护针对的是**不同等级的攻击**，这叫纵深防御：

| 攻击等级 | 攻击者能拿到什么 | 谁挡住它 |
|----------|------------------|----------|
| 匿名网络访问 | 什么都摸不到 | 防火墙（只开 22/80/443）+ HTTPS + 访问口令 |
| 拿到口令的普通用户 | 只有自己的存档 | JWT 校验 + 存档归属校验（404） |
| 拖走数据库文件 | 存档明文 + 密码**哈希** | scrypt 加盐——**密码本身反推不出来**（用户可能在别处复用同一密码，这是最关键的保护） |
| 拿到服务器 root 权限 | 一切 | 没有技术手段能挡——靠**预防**：SSH 密钥登录、及时打补丁、最小权限、备份与监控 |

**关键洞察**：密码存哈希不是为了防『服务器被攻破』，是为了**限制攻破的损失**——数据库被拖走后，攻击者拿到的密码哈希无法直接登录**本站以外的任何网站**。如果存的是明文，一次拖库 = 所有用户的密码全网泄露。这就是『限制爆炸半径』的思想：假设每一层都会失守，让每一层失守时损失最小。

**被攻破后怎么办**（亡羊补牢清单）：改掉 ACCESS_TOKEN 和 JWT_SECRET（旧令牌全部失效）→ 通知用户改密码 → 从备份恢复数据 → 排查入侵路径。所以**异地备份**也是安全体系的一部分——它防的不只是攻击，还有机器故障。

**Q：访问口令能被暴力破解吗？没拿到口令是不是服务器就绝对安全？**

两个问题分开答：

**口令本身能不能暴力破解？** 没有像登录那样的失败锁定——口令中间件只做逐次比对，不限速。所以防暴力破解**完全依赖口令自身的强度**：口令是长随机串（如 32 位十六进制）时，穷举空间 16³² ≈ 10³⁸，每秒试一万次也要 10³⁰ 年——实际不可行；但如果口令是人类好记的弱口令（如 `abc12345`），无限速的比对接口就是暴力破解的温床。**结论：口令请用长随机串，不要用人类密码。**

**没拿到口令，服务器就绝对安全了吗？不是。** 口令只保护了**游戏 API 这一层**，服务器的其他攻击面与口令无关：

| 攻击面 | 与口令的关系 |
|--------|--------------|
| SSH（22 端口） | 无关——攻击者可直接对 SSH 做密码爆破/密钥碰撞，靠的是 SSH 自身的防护（密钥登录、禁用密码登录） |
| Caddy/Web 服务（80/443） | 无关——Web 服务器软件自身有漏洞时，攻击者可绕过应用层直接攻击 |
| 操作系统与依赖漏洞 | 无关——内核、glibc、npm 依赖包的漏洞都可能直接给攻击者提权 |
| 静态页面 | 口令**不保护**静态文件——页面 HTML/JS 本身是公开下载的（口令只拦 /api） |

所以正确的安全观是：**口令只是纵深防御中的一层**（挡住『匿名者直接调游戏 API』），不是服务器的整体安全。服务器的整体安全靠：防火墙最小端口开放 + SSH 密钥登录 + 系统及时更新 + 依赖审计 + 备份。没有任何单一措施能让服务器『绝对安全』。

**Q：不知道口令的人，能下载到的是口令输入页还是整个网站？**

**整个前端都能下载**——实测（不带口令直接请求）：首页 HTML 返回 200、整个 JS 包（约 160KB）返回 200、CSS 返回 200，只有 /api 被拦。原因：『口令输入页』不是服务器上的一个独立页面——它是**同一个 Vue 应用的一部分**。浏览器下载完整 JS 包后运行它，应用自己判断『没有口令记录 → 显示口令界面』。这个判断发生在**浏览器里**，服务器无法只发『口令那一页』。

**这算泄密吗？不算。** SPA（单页应用）的常规形态就是这样：前端代码本来就是『发给浏览器运行的程序』，设计上就是公开的。关键在于代码里**没有秘密**：
- 谁是狼人、存档内容、用户数据——全在后端数据库，前端代码里一行都没有；
- 口令本身、JWT 密钥——在服务器 `.env`，前端代码里只有『读 localStorage 里的口令』这个逻辑，没有口令的值；
- 攻击者读完全部前端代码，能知道 API 的路径和参数格式，但依然过不了口令与登录两道门。

**一个推论**：前端代码里出现的任何值都应视为公开。这就是为什么密钥永远放 `.env`、游戏真相永远只在后端——不是『藏在前端代码的角落里』，而是根本不放进前端。

**Q：有没有办法避免前端被完整下载？会被爬虫『攻击』吗？**

**能避免，但通常没必要。** 技术上可行的方案：

| 方案 | 做法 | 代价 |
|--------|------|------|
| 反代层加认证 | 在 Caddy 对静态文件加 basic_auth，未认证连 JS 包都拿不到 | 每个新设备都要过一次浏览器原生认证框，体验变差；且和口令功能重复 |
| 服务端渲染（SSR） | 页面由后端按登录态动态生成，未登录只发登录页 | 架构大改，失去 SPA 的轻量优势 |
| 代码混淆 | 把 JS 压缩混淆到难以阅读 | 防君子不防小人——决心逆向的人总能还原，只是增加成本 |

**为什么没必要**：本项目的源码本来就公开在 GitHub 上——保护服务器上那份编译产物没有意义，秘密从来不在前端。混淆只对『代码本身是商业机密』的产品有价值。

**爬虫会来吗？会，但那不是攻击。** 要区分两件事：
- **爬虫抓取静态页面**（搜索引擎索引、安全扫描器）：它们下载 HTML/JS 只是正常访问公开文件。实测完整加载一次约 110KB（HTML 0.4KB + JS 压缩后 58KB + CSS 压缩后 8KB——Caddy 已开启 gzip/zstd 压缩，未压缩时约 213KB）——单次量不大，且 JS/CSS 文件名带哈希、浏览器会缓存，重复访问只拉 0.4KB 的 HTML。爬虫高频抓取才需要在意带宽，正常零星抓取无影响。不希望被搜索引擎收录可以放一个 `robots.txt` 声明；
- **机器人刷 API**：这才是真正的风险——脚本反复调用 AI 接口烧掉你的 LLM 账单。而这正是口令 + 失败限速防住的东西：没有口令的请求在第一道门就被拒，连 LLM 的边都摸不到。

**一句话**：爬虫下载前端 = 有人看了你公开的传单；机器人刷 API = 有人偷用你的钱包——前者无害，后者已被口令挡住。

**Q：未输入口令的情况下，有没有可能错误地显示其他界面（而不是口令页）？**

正常情况不会——门禁组件（AccessGate）挂载时先发一个探测请求，验证完成前**不渲染任何游戏内容**（probing 标记挡住）。但存在三个边界情况：

| 情况 | 表现 | 是 bug 吗 |
|------|------|----------|
| 后端不可达（宕机/网络错误，非 401） | **故意放行**显示游戏界面——但界面是空壳，所有请求失败、错误条提示 | 不是，是设计取舍：让用户能看到页面并从错误信息排查『后端没起』，而不是卡死在口令页什么都看不到 |
| 口令中途过期（游玩中 7 天到期） | 界面**不会自动弹回口令页**——下一个请求 401，错误显示在游戏界面的错误条上，需刷新页面才重新探测 | 算体验瑕疵：功能上安全（数据拿不到），但提示不够直观 |
| 用户用浏览器开发者工具篡改前端内存（改 authed 变量） | 可以让口令页消失、显示游戏界面 | 无所谓——前端只是『壳』，所有 API 请求依然被后端 401 拒绝，拿不到任何数据。看到界面 ≠ 能玩 |

**核心原则**：前端界面显示什么只是『视觉问题』，真正的门禁在后端——每个 API 请求都独立校验口令。就算界面被骗过去显示出来，没有口令的请求一个都过不了，页面只是空壳。

**Q：JWT 令牌存在前端哪里？被偷了怎么办？**

存在浏览器的 localStorage（一个按域名隔离的键值仓库，刷新不丢）。被偷的风险主要来自 XSS（页面被注入恶意脚本读取 localStorage）——本项目前端不渲染任何用户提供的 HTML，输入都以纯文本处理，XSS 面很小。令牌本身有 72 小时有效期兜底：过期自动失效，必须重新登录。修改用户名/密码这类敏感操作还会**再验一次密码**（不是只看令牌），就算令牌被盗也改不了账号。

**Q：为什么用 localStorage 而不是 Cookie？**

Cookie 每个请求自动携带（方便），但会被 CSRF 攻击利用（别的网站诱导你的浏览器发请求）。localStorage 不会自动发送——必须代码手动加 Authorization 头，别的网站拿不到也发不出，天然免疫 CSRF。代价是要防 XSS（见上一问）。两种方案各有取舍，本项目选了后者。

**Q：HMAC-SHA256 签名为什么伪造不了？**

签名 = HMAC(内容, 密钥)。HMAC 是带密钥的哈希：不知道密钥时，给定任意内容都算不出正确签名。攻击者可以随意改载荷（比如把 uid 换成别人的），但改完后第三段签名就对不上了——服务器重算一遍立刻识破。而密钥只存在服务器 `.env` 里，从不下发。

**Q：载荷里的 uid 明明能看到，为什么不加密隐藏？**

JWT 的签名只保证『不可篡改』，不保证『不可看』——载荷只是 base64（一种编码，不是加密），谁都能解开看。这没关系：uid 本身不是秘密，泄露了也没有用处（没有签名就伪造不了令牌）。JWT 的设计目标就是完整性，不是保密性。

**Q：登录失败限速为什么存在？防的是什么攻击？**

防**暴力破解**——攻击者写脚本成千上万次试密码。限速规则：同一用户名连续失败 5 次 → 锁 10 分钟。这让每次尝试的成本从『毫秒级』变成『至少 2 分钟一次』，穷举 6 位密码需要的时间从几小时变成几百年。注意：限速记录存在内存 Map 里，重启服务会清零——这是可接受的权衡（重启窗口极小）。

**Q：为什么存档存整个 JSON，不拆成玩家表、消息表？**

游戏对象结构随模式不同、随开发频繁变化——拆表意味着每次改字段都要改表结构（数据库迁移），成本高。存 JSON 则『整存整取』，内部结构随便改。代价是 SQL 查不了内部字段（不能直接查『第 3 天谁死了』）——但本项目存档只需要整取，这个取舍划算。这叫**文档式存储**，MongoDB 等文档数据库就是这个思路的极致。

**Q：JSON.stringify / JSON.parse 到底做了什么？**

`stringify` 把 JS 对象变成文本：`{a:1}` → `"{"a":1}"`（注意键加了引号）；`parse` 是逆操作。存数据库必须先 stringify（数据库只存文本/数字），读出来再 parse 还原成对象。

**Q：为什么临时脚本里 require 要写全路径？**

Node 找模块的规则是『从当前文件所在目录向上逐级找 node_modules』。脚本放在 `/tmp`，`/tmp` 及其上级目录没有 node_modules，所以裸写 `require('better-sqlite3')` 会报 `MODULE_NOT_FOUND`。写全路径 `/项目/server/node_modules/better-sqlite3` 是直接指到文件，绕过查找规则。

**Q：`.get()` 和 `.all()` 有什么区别？**

都是执行查询：`.get()` 返回**第一条**结果（没有则 undefined），适合按 id 查单个；`.all()` 返回**全部**结果的数组，适合列表查询。还有 `.run()`——执行写入（INSERT/UPDATE/DELETE），返回受影响行数。

# 第二部分：多模式 + 世界观架构详解

### 2.4 多模式 + 世界观架构

这是本项目与"单一题材文字冒险"最大的区别，是后续扩展（如探案）的地基。

#### 2.4.1 游戏模式（Mode）——可插拔

`server/modes/index.js` 是一张模式注册表：

```js
const MODES = { [world.modeId]: world };   // 新增模式只需在此登记
function getMode(id) { return MODES[id] || null; }
function listModes() { /* 返回 [{id, name, needsTheme}] 供前端渲染 */ }
```

每个模式模块需导出统一契约，路由**只认契约、不认具体模式**：

| 导出 | 作用 |
|------|------|
| `modeId` / `modeName` | 模式标识与展示名 |
| `needsTheme` | 是否需要世界观配置（大世界为 `true`） |
| `newGame(name, { theme })` | 初始化一局游戏 |
| `processAction(game, input)` | 核心回合处理（提示词 + LLM + 状态应用） |
| `useItem / discardItem / equipItem / unequipItem / cancelPendingAction` | 物品按钮操作 |
| `summarize(game)` | 存档摘要 |

> 已有实例：**探案（`detective`）** 正是在不修改 `index.js` 路由的前提下通过注册表接入的——它注册了 `needsGenre`（题材）与探案专用接口 `accuse` / `confront`、`GET /case`，路由层仅新增了这几个探案专属 URI，核心 `/action` 循环仍走统一契约分发。前端首页从 `/api/modes` 动态渲染出「探案」卡片与题材选择。

#### 2.4.2 世界观配置（Theme）——数据驱动

一个 Theme 描述了"这个世界长什么样、玩家能做什么"：

```jsonc
{
  "id": "azeroth",
  "name": "艾泽洛姆",
  "intro": "中世纪奇幻大陆……",
  "capabilities": {
    "hasCombat": true,                       // 是否有战斗
    "statSchema": ["hp", "gold", "exp"],     // 启用哪些数值
    "itemCategories": ["weapon", "armor", "item"], // 有哪些物品类别
    "slots": [                               // 有哪些装备槽
      { "id": "weapon", "label": "武器" },
      { "id": "armor", "label": "防具" }
    ]
  },
  "startState": { "hp": 100, "gold": 10, "inventory": ["干粮 x2"], "slots": { "weapon": "武器·旧铁剑[普通]" } },
  "gmGuidelines": "该世界特有的叙事约束"
}
```

**capabilities 是"通用化"的关键**：它同时驱动后端提示词与前端 UI，从而支持任意题材：

| 世界观举例 | hasCombat | statSchema | itemCategories | slots |
|-----------|-----------|------------|----------------|-------|
| 中世纪奇幻（艾泽洛姆） | true | hp, gold, exp | weapon, armor, item | 武器、防具 |
| 现代悬疑 / 解谜 | false | hp | item | （无） |

`server/themes/index.js` 的 `normalizeTheme()` 会做安全兜底：至少保留 `hp`、至少保留 `item` 类别；若没有 `weapon`/`armor` 类别，则**自动移除对应装备槽**，并让 `startState.slots` 的键与 `slots` 完全对齐 —— 保证引擎取用安全。

#### 2.4.3 纯文本世界观 → 可玩配置

玩家在首页粘贴一段世界观文本，后端 `themes.parseThemeFromText()`：

1. 用一段**元提示词**要求 AI 只输出符合 Theme 结构的 JSON（明确"无需战斗时必须 `slots: []`、`itemCategories` 只含 `item`"等规则）
2. 复用 `parseActionJson()` 容错解析
3. 经 `normalizeTheme()` 规范化后返回前端
4. 前端把该对象随"新建游戏"请求带回，落库到存档的 `theme` 字段

> 该接口**不落盘**：自定义世界观随具体存档保存，不污染内置模板目录。

#### 2.4.4 能力驱动的 UI（前端）

`frontend/src/composables/useGame.js` 通过 `provide('game', ...)` 暴露模式无关的状态与操作；`WorldView.vue` 按 `state.theme.capabilities` 动态渲染：

```js
const caps  = computed(() => state.theme?.capabilities || { ...默认值 });
const stats = computed(() => caps.value.statSchema);   // 决定显示 HP / 金币 / 经验条
const slots = computed(() => caps.value.slots);         // 决定渲染哪些装备槽
const hasItem = computed(() => caps.value.itemCategories.includes('item'));
```

因此同一套前端可渲染"有武器防具的奇幻世界"与"只有背包的现代世界"，无需分支硬编码。

#### 2.4.5 探案设计（案件驱动的确定性结算）

探案与"大世界"最大的区别：**真相由代码持有，AI 只负责演绎**，防止真相漂移。

**案件真相（`game.case`）** —— 生成时由 AI 产出、经结构校验后落库：

| 字段 | 说明 |
|------|------|
| `culpritId` / `victim` | 凶手 / 死者（含死因与发现信息） |
| `crime` | 动机 / 手法 / 时间窗 / 破绽 |
| `suspects[]` | 嫌疑人：`isLiar`（说谎者）、`statements[]`（口供，`truth` 标记真假）、`rebuttalEvidenceId`（能击破他的物证）、`onRebuttal`（被击破后交代的真相与撒谎原因） |
| `evidence[]` | 物证：`foundAt`（发现场景）、`rebuts[]`（能反驳哪些嫌疑人，含说谎者与凶手） |
| `scenes[]` | 场景：`npcs`（在场人物），探索范围明确、无法无穷自由探索 |
| `keyClues[]` | 关键线索 id（2~4 条，**不得来自凶手、也不得来自死者**），举证时按覆盖率判定认罪 |

**题材（`GET /api/genres`）**：现代都市 / 古代衙门 / 民国旧案 / 奇幻王国 / **蒸汽时代**（维多利亚式欧洲推理，`server/casegen.js` 的 `GENRES` 注册即可，前端自动渲染）。

**案件生成的结构硬约束**：
- **死者绝不能出现在 `suspects` 中**（`normalizeCase` 按「与 `victim.name` 同名 / identity 含 受害·死者·被害人」确定性剔除；`validateCase` 也会拦截）。死者的言论只能由活着的证人转述（如「（管家口述）凌女士那晚曾说…」），keyClues 必须来自可盘问的活人——否则会出现"玩家永远拿不到的关键证据"。
- **keyClues 自动修复兜底**：`normalizeCase` 在归一化后检查——若 keyClues 没有说谎者的真话，直接从已归一化的口供中补选 1 条（模型常漏选，触发「至少 1 条来自说谎者真话」校验反复失败）；不足 2 条时从非凶手真话中补足；上限 4 条。生成重试上限 `MAX_ATTEMPTS = 5`。

**确定性结算（代码判定，AI 只演绎）**：

| 事件 | 判定 |
|------|------|
| 场景切换 | 按钮通道（`scene` 参数）或文字通道 `matchScene()` 三级匹配：场景 id → 完整场景名 → **移动意图词 + 场景独有片段**（支持省略公共前缀的简称，如「云岭大厦物业前台」→「前往物业前台」；无移动意图词不触发片段匹配，避免"提及场景名"被误判为移动）→ 代码移动 `detective.currentScene` |
| 发现物证 | 行动命中物件物证所在场景的关键词 → 代码将「物证·xxx」放入背包 |
| 击破谎言 | 玩家**装备**物证并当面质问在场嫌疑人，且物证 `rebuts` 命中该人（**不限于说谎者，凶手也可被击破**）→ 代码判定击破。说谎者全盘交代真相+撒谎原因；凶手被击破后只会**部分坦言**（如承认到过现场，但绝不直接自证杀人，认罪仍须走举证） |
| 指认凶手 | `detective.accuse(id)`：命中 `culpritId` → 进入对质；否则 `hp -25`，归零则游戏失败 |
| 举证认罪 | `detective.confront(clueIds)`：提交的线索中命中 `keyClues` 的覆盖率 ≥ `CONFESS_RATIO(0.6)` → 凶手认罪、胜利；失败不扣血、线索不消耗 |
| 无效行动拦截 | `quickNoopReply()`：盘问**已问尽的诚实 NPC**（口供全取得且非说谎者/凶手）或**重复搜索已搜遍的场景**（无未发现物证）→ 程序直接返回一句简短反馈与引导选项，**不调 LLM**，杜绝"人人疑神疑鬼 + 无效推进冗长" |

**游戏状态（`game.detective`）**：`phase`（`investigate → confront → win/lose`）、`clues[]`（已获得的线索及真伪标记）、`evidenceIds`、`revealed[]`（已被击破的人）、`failedAccusations`、`currentScene`。

**快照防剧透（`snapshot()`）**：下发给前端的探案状态**剔除一切真相字段**（`isCulprit/isLiar/truth/culpritId/keyClues/crime`）；完整案件说明只由 `GET /api/games/:id/case` 在玩家于前端主动展开（二次确认后）时下发。快照额外提供：
- `evidence[]`：物证明细（`name/desc/foundAt` 场景名），前端物证栏展示描述
- `caseResult`：**仅 `win` 阶段**携带的证据复盘 `{ got:[{text,holder}], missing:[{text,holder}], total }`（命中/未获取的关键证据），调查阶段为 `null` 不泄露
- 前端**案卷详情**（`GET /case` 下发完整真相后展示）：凶手/说谎者标签、撒谎动机 `lieMotive`、被击破后的反应 `onRebuttal`、口供逐条真/假标记、「关键证据（足以锁定凶手）」清单——按 `keyClues` 反查口供文本与持有人

**叙事风格约束**：
- 诚实 NPC（非说谎者、非凶手）说话**坦然直接、配合调查**，不渲染心虚；只有说谎者/凶手在隐瞒时才有躲闪紧张的表现（提示词规则 4.2）
- narrative 字数弹性：**有实质进展 150~350 字 / 无进展 60~120 字**（替代原固定 300~500 字）

**物体操作延续硬约束**：线索与物证均以「线索·/物证·」前缀物品进入背包；装备、卸下、举证勾选等均由前端按钮完成，AI 只结算与演绎。

#### 2.4.6 狼人杀模式设计（身份驱动的发言博弈）

狼人杀与探案共享同一架构信念：**身份真相由代码持有，AI 只按身份发言与投票**。首版为 MVP：玩家固定好人（村民）、5 人局（1 狼 + 1 预言家 + 3 村民）、夜晚无交互。

**游戏状态（`game.wolf`）**：

| 字段 | 说明 |
|------|------|
| `players[]` | 5 人：`id/name/role(wolf\|seer\|villager)/isPlayer/alive`（role 为真相，快照剔除） |
| `phase` | `day（玩家发言）→ vote（玩家投票）→ win / lose` |
| `round` | 当前天数（每放逐后+1，进入新夜晚） |
| `speeches[]` | 本轮全部发言（`{round, playerId, name, speech}`），供后发言者参考 |
| `suspect{}` | 每个 AI 的怀疑目标（LLM 在发言中给出，投票时使用） |
| `deaths[]` | 死讯（`cause: night` 身份不公开 / `vote` 身份公开） |
| `night` | 最近一夜结算：`killedByWolf / seerTarget / seerResult` |

**确定性结算（AI 只演绎，不决定结局）**：

| 事件 | 判定 |
|------|------|
| 夜晚（狼刀 + 验人） | `settleNight()`：狼刀目标 = 狼人 `suspect`（首夜保护玩家不刀）；预言家验人结果写入 `night`，供其发言引用。**无 LLM 调用**，天亮直接给死讯 |
| 白天发言 | 玩家先发言（文字输入）→ 依次对每个存活 AI 生成一次发言（LLM，`generateSpeech`）。每个 AI 的提示词带「自己的身份 + 之前的全部发言」：狼人伪装/圆谎/带票，预言家可公布验人，村民凭矛盾推理。输出 JSON `{"speech","suspect"}`；失败回落模板保证回合不断 |
| 投票放逐 | 玩家按钮 1 票 + 每个存活 AI 按 `suspect` 投 1 票 → 唯一最高票者被放逐并**公开身份**；平票无人放逐 |
| 胜负判定 | `checkWinner()`：狼死 → 好人胜；玩家死 / 好人阵营仅剩玩家 → 狼人胜。**白天投票后与夜晚结算后各判定一次**（狼夜刀可能直接达成胜利条件） |
| 终局复盘 | 游戏结束揭示全部身份（`roles`），前端展示 |

**快照防剧透（`snapshot()`）**：`players` 只含 `id/name/alive/isPlayer`，**绝不含 `role`**；`roles` 仅终局时非空；`playerRole` 只对玩家本人可见（其身份本就公开）。AI 狼人/预言家的验人结果只在叙事中由对应角色按策略说出，绝不直接下发前端。

**发言引擎要点**：narrative 由多段「角色名：发言」拼接展示，先发言者可引用前序发言做出反应（质疑/辩解/带票），形成真实的发言博弈；`suspect` 由 LLM 给出后经 `pickSuspect` 校验（存活、非自己），投票据此落地。

#### 2.4.7 推理杀模式设计（法官视角的甄谎推理 · 7 人局多角色）

**AI 发言采用结构化三层架构**（杜绝规则幻觉与行为泄露，经 8 局完整对局逐人评估迭代验证，连续 2 局零问题）：
1. **事实骨架**：程序从知识包确定性生成每轮必须交代的事实行；带伪装者只保留伪装行为素材，真实技能结果绝不进入骨架；
2. **措辞润色**：LLM 只负责把骨架改写为自然口语（不得增删事实），提示词注入 17 个角色的官方技能说明（仅供理解、不得复述）；
3. **输出校验**：引号内名称必须在玩家名/角色名/阵营名白名单内；规则断言词（中毒/自毙/误验等）必须来自骨架；素材照抄（含【】标记）直接提取陈述句或兜底——校验失败一律回退确定性兜底发言。

配套机制：伪装分配防撞车（坏人之间、中立与坏人/其他中立互不重复）；间谍撒谎指令与可公布说法分行（指令绝不进入发言）；小丑扭曲发言代码级反转并清洗标记；守卫自保用第一人称文案。

推理杀把玩家从「参与者」变成「**法官**」：不参与游戏、不会出局，只观察 AI 发言并裁决处刑。它复用"真相代码持有"架构，但**信息量大幅提升**——好人给真信息、坏人给假信息、中立搅局，夜晚技能互相干扰，核心乐趣是交叉验证。

**规则要点**：

| 项 | 配置 |
|----|------|
| 人数 | **7 人局，全部 AI**：4 好人 + 1 中立 + 2 坏人 |
| 好人 | 从「文员/侦探/村民/法医/守卫」**不重复选 4**（信息维度每局不同） |
| 中立 | 「赌徒/小偷」二选一（无独立胜利，默认自保+搅局） |
| 坏人 | 必含 1 狼，另一为「帮凶/酒鬼」；**狼唯一**，狼死后同伴继承变狼 |
| 玩家 | 法官：不参与、不死，看死讯、听发言、裁决 |
| 死讯 | 被刀**不亮身份**（与狼人杀对齐）；被处刑**公开真实身份牌** |
| 裁决 | 处刑某人（公开身份牌）或放弃（无人放逐、进下一夜） |
| 胜负 | 场上无存活狼（含变身新狼）且坏人同伴全灭 → 好人胜；好人阵营全灭 → 狼胜 |

**角色定义**：

| 角色 | 阵营 | 夜晚 | 技能 |
|------|------|------|------|
| 文员 | 好 | 不出门 | 开局即知本局角色名单（首轮公布，后续无技能）；被清记忆仍能报名单（越常信息） |
| 侦探 | 好 | 出门 | 探访一人，获得「他昨夜是否外出活动」线索。注意：没有外出 ≠ 安全（狼可入室行凶） |
| 村民 | 好 | 不出门 | 无技能；被拜访会知道"有人来过"（被清记忆则只说忘记了） |
| 法医 | 好 | 第 1 夜不出门，第 2 夜起 | 前往上一案发现场，次轮公布死者真实身份 |
| 守卫 | 好 | 出门 | 守护一人：若恰为狼刀目标则挡下（平安夜）。可自保、不能连续两夜同一人；只掌握守护对象情况 |
| 赌徒 | 中立 | 不出门 | 猜一人阵营（好人/中立/坏人）：猜对获其阵营信息，猜错立即死亡 |
| 小偷 | 中立 | 出门 | 拜访一人：若目标本夜死亡 → **获取死者"原本要进行的动作"信息**（守卫原想守谁/侦探线索/法医结论/赌徒结果）；若存活 → 清其记忆（技能失效、只说"忘记了"）；访狼 → 狼本夜刀无效 |
| 狼人 | 坏 | 出门 | 刀一人（可杀任何人在家与否）；首夜不可刀文员。**绝不承认刀人**，伪装成好人身份发言 |
| 帮凶 | 坏 | 出门 | 知道狼人是谁，为其掩护或栽赃；狼死后继承变狼 |
| 酒鬼 | 坏 | 不出门 | 拜访者被迷醉（技能失效、只说"忘记了"）；狼死后继承变狼 |

**游戏状态（`game.deduction`）**：`players[]`（含 role 真相与 cover 伪装）、`phase`（`day → adjudicate → win/lose`）、`round`、`speeches[]`、`suspect{}`、`deaths[]`（内部含 role，快照隐藏）、`night`（每夜结算明细）、`nightLogs[]`（逐夜行动记录，终局回顾）、`claims[]`（发言中提取的自称身份）。

**多阶段夜晚管线（全确定性，AI 不参与）** `settleNight()`：

```text
阶段 0  变身      帮凶/酒鬼继承狼（可链式：狼→帮凶→酒鬼）；变身后当夜即可行动
阶段 1  锁定行动  各角色选目标（狼刀/守卫守护/侦探·帮凶·小偷拜访/赌徒猜阵营/法医取材）
阶段 2  酒鬼迷醉  拜访酒鬼者技能无效（若酒鬼被刀死则迷醉不触发——两遍修正循环依赖）
阶段 3  小偷标记  清目标记忆 / 访狼则狼刀失效
阶段 4  守卫保护  守中狼刀目标 → 平安夜
阶段 5  狼刀结算  狼未被迷醉/遗忘则出刀
阶段 6  赌徒猜测  猜对获阵营信息，猜错立即死亡
阶段 7  死亡落盘  狼刀死者 + 赌徒自食其果
阶段 8  小偷继承  目标死亡 → 获取其"原本要进行的动作"信息（守卫原守护目标/侦探线索/法医结论/赌徒结果）
阶段 9  知识包    按角色生成私有发言素材（含被迷醉/遗忘/证伪等状态）
```

**天色与裁决**：

| 事件 | 判定 |
|------|------|
| 首轮身份声明 | `assignCovers()` 程序注入：好人 = 真身份；坏人 = 池中抽取两个**互不相同**的伪装身份（本局有文员时排除文员，防跳文员给不出名单）；中立随机真/假 |
| 身份冲突引导 | 第 2 轮起：有人自称与你的**真实身份**相同（真守卫 vs 假守卫）→ 知识包强制当众质疑"同一身份不可能有两人" |
| 白天发言 | `processAction()`：法官不发言，存活 AI 依次发言。**被迷醉/遗忘者固定一句"忘记了"**（硬规则不走 LLM）；其余按知识包 + factLine 组织（见下） |
| 发言质量保障 | LLM 输出过短（<24 字）或坏人自曝（"我是狼人"等）→ 代码级替换为 `fallbackSpeech`（各角色成句 + 长度保险，保证信息量） |
| 自称身份 | `claims` 从发言文本提取「我是X」（`extractClaim` 支持"我是名字，身份"），前端建速记面板并高亮同名冲突 |
| 法官裁决 | `adjudicate(targetId)`：处刑 → 公开真实身份牌 → 判胜负（**三阵营文案**：狼/好人/中立/帮凶酒鬼 各不同）；放弃（空 targetId）→ 进下一夜。夜晚后二次判胜负 |
| 终局 | 全部身份揭示 + **逐夜行动回顾**（`nightLogs` 数据随终局快照下发，前端 `formatNightLog` 以『执行者（角色）动作「目标」：结果』格式渲染为关系图下说明文字）；复盘含 `roleBackup`（变身者原本身份）与 `turnedRound`（变身轮次），前端显示为『原本身份（第N夜变身狼人）』 |

**逐夜行动关系图（NightActionGraph.vue）**：
- 数据来源：终局快照的 `nightLogs`（每晚各方行动）+ `roles`（真实身份，含变身轨迹）；
- 渲染：SVG 环形布局——人物为节点（名字+真实身份，按阵营着色：好人蓝/中立黄/坏人红，当夜死者带 💀），行动为二次贝塞尔曲线边（带箭头，按行为类型着色：刀杀红/保护绿/探访蓝/窃紫/迷醉红等），线上标注行为与结果（如『刀杀』『保护』『猜·坏人·殒命』『命运链接』）；
- 自环处理：守卫自保等自指行动以节点上方小弧表示；多条边错开弧度避免重叠；
- 中间人物避让：连线生成时采样贝塞尔曲线检测是否穿过连线双方之外的第三方人物框，若穿过则依次尝试另一侧偏移与逐级加大弧度（正/反两侧 × 4 档弧度），取首个无碰撞方案；全部碰撞时保留碰撞人数最少的方案（避免『保护线穿过周舟』类遮挡问题）。

**弹窗时序编排（前端 watch 链）**：
- 处刑后服务端同批次返回处刑结果与新一夜/终局信息，前端以 `pendingNightEvent`/`pendingEndModal` 暂存待播；
- 处刑结果弹窗关闭（execResult 置空）后依次释放暂存弹窗，保证『处刑结果 → 夜间事件 → 终局结算』顺序；
- 夜间事件弹窗的死者名字延迟揭示：骷髅图标落砸（0.2s 起 0.7s）与震动（0.9s 起 0.6s）动画播完后，死者名字才从 1.5s 起逐个淡入（每人间隔 0.3s），避免名字先于动画效果出现造成剧透感；
- 全部弹窗使用 Vue Transition 包装，展开为弹性缩放动画、收回为缩小下沉+遮罩淡出。

**发言约束（`factLine` 硬规则）**：

1. 第一人称【完整交代信息】：先说「我是X」，再把素材里的技能结果/亲历事件如实转述；禁止只报身份就结束
2. 诚实角色说真话、坏人按知识包编造伪装行为、中立自选
3. 【技能真实·铁律】只能声称行使真实拥有的能力，严禁编造"查验/占卜/鉴定身份"等不存在的技能
4. 【信息边界·铁律】只能陈述素材明确提供的信息，不得虚构身份无法观测的情报（如守卫声称"留意到他人动向"）；信息多但宁实勿虚
5. 坏人绝对禁止在发言中提及真实夜间行动（如"我刀了X"）
6. 游戏常识：「在家/没有外出」不等于「没被袭击」，不能据此反驳他被刀了
7. 非首轮坚持同一声明（`cover` 伪装者整局伪装、坦白者整局坦白），杜绝轮间漂移

**快照防剧透（`snapshot()`）**：`players` 只含 `id/name/alive`，绝不含 `role`/`cover`；`deaths` 中 `cause='night'` 不带身份、`cause='execute'` 带身份牌；`roles` 仅终局非空；`nightLogs` 仅终局返回；前端**不直接下发角色名单**（那是文员的职责），`clerkPoolRevealed` 标记文员是否已公布名单。

# 第三部分：AI 交互实现详解与关键知识点

### 2.5 AI 交互实现详解

本节说明游戏与 AI 交互的三个核心问题：**如何连接 AI、如何把世界观交给 AI、如何约束 AI 的输出**。

#### 2.5.1 连接 AI（server/llm.js）

- 项目**不依赖任何 AI SDK**，使用 Node.js ≥18 内置的 `fetch` 直接请求 OpenAI 兼容的 `/chat/completions` 接口
- 请求参数来自环境变量（`.env`）：`LLM_BASE_URL`（服务地址）、`LLM_API_KEY`（密钥）、`LLM_MODEL`（模型名）
- 由于遵循 OpenAI 兼容协议，**只需改 `.env` 即可切换任意兼容服务**（OpenAI 官方、Sensenova、DeepSeek、国内中转等）
- 认证方式：标准 `Authorization: Bearer <API Key>` 请求头
- 60 秒超时自动中断，防止模型响应卡死

**当前请求参数（针对 sensenova 系列调优）：**

| 参数 | 值 | 为什么 |
|------|-----|--------|
| `temperature` | 0.9 | 剧情随机性，创意写作偏高 |
| `max_tokens` | 4096 | 官方推荐普通任务额度（2048~4096）；系统提示词+历史已占约 2000 token，2048 时输出被截断导致 JSON 解析失败、触发降级 |
| `reasoning_effort` | `"none"` | **关闭思考模式**（sensenova 思考默认开启，会抢占输出配额导致空内容） |
| `response_format` | `{type: "json_object"}` | 结构化输出，要求返回合法 JSON |

```js
// 核心调用（真实参数）
await fetch(`${cfg.baseUrl}/chat/completions`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${cfg.apiKey}` },
  body: JSON.stringify({
    model, messages, temperature: 0.9, max_tokens: 4096,
    reasoning_effort: 'none',
    response_format: { type: 'json_object' },
  }),
});
```

#### 2.5.2 世界观与状态的传递（server/modes/world.js → buildSystemPrompt）

每次调用 AI 前，模式处理器会**按世界观能力动态构造**系统提示词（system prompt）：

| 提示词组成部分 | 内容 | 作用 |
|---------------|------|------|
| **角色设定** | "你是「{世界名}」的至高游戏主持人（Game Master）" | 定义 AI 的身份与职责（世界名来自 Theme） |
| **输出协议** | 必须输出指定结构的 JSON（见 2.5.3） | 让 AI 的返回可被程序解析 |
| **字段填写规则** | 按 `statSchema` / `itemCategories` **裁剪**的 delta 规则 | 无金币的世界不会有金币规则 |
| **物品操作权限** | AI 无权移动物品（仅当有物品类别时注入） | 物品移动一律由前端按钮完成 |
| **道具效果规则** | 食物回血、毒物扣血等（仅当有 item 类别时注入） | 无预设效果表，效果由 AI 判定 |
| **物品品质规则** | 武器「武器·名称[品质]」、防具「防具·名称[品质]」（仅当有武器/防具时注入） | 统一命名与稀有度 |
| **剧情原则** | 不替玩家做决定；含 hp 时才加死亡规则 | 保证玩法一致性 |
| **世界观** | `theme.intro` + `gmGuidelines` | 统一叙事背景，防止 AI 跑偏 |
| **当前状态** | 玩家姓名/等级/HP/金币/装备/背包（`renderPlayer()` 按能力裁剪） | 让 AI 知道实时数据，据此填 delta |
| **剧情回顾** | 最近 6 条对话历史 | 保证前后剧情连贯、承接上一回合 |

这套提示词在**每回合都重新生成**，因为玩家状态和历史在持续变化。它就是"游戏规则"和"AI 行为"之间的桥梁。

#### 2.5.3 约束 AI 输出（多层防护架构）

AI 是"尽力遵守协议"的，不能指望它永远正确。本项目用**五层防护**确保游戏稳定：

**第 1 层 · 协议约束（提示词中强制）**

提示词明确要求 AI 只输出如下 JSON（delta 字段按世界观裁剪），不得输出其他文字：

```json
{
  "narrative": "本回合剧情，300~500字，第二人称，结尾不替玩家做决定",
  "choices": ["建议选项A", "建议选项B", "建议选项C"],
  "delta": { "hp": 0, "gold": 0, "exp": 0, "inventory": ["获得的物品"] },
  "battle": true
}
```

并附带数值规则：hp 幅度 5~40、gold 幅度 1~50、exp 幅度 10~30、未发生的事填 0 或空数组、死亡时 delta.hp 恰好归零等。

> **物品操作权限**：delta 中只有 `inventory`（AI 赠送的新物品，进入背包）。**使用 / 丢弃 / 卸下 / 装备物品由玩家通过前端按钮完成并自动同步**，AI 无权移动任何物品（`removeInventory` / `weapon` / `armor` 字段已被后端硬性忽略），只负责在剧情中描写按钮动作并结算其效果（如食用食物 → hp 回血）。

**第 2 层 · 参数约束（请求级）**

请求携带 `response_format: { type: "json_object" }` 从接口层要求 JSON 输出。**注意**：这是"软约束"——实测部分模型（如 sensenova-6.8-flash-lite）仅约 1/3 概率真正生效，因此还需要后续层兜底。

**第 3 层 · 容错解析（`parseActionJson`）**

- 兼容 AI 把 JSON 包在 markdown 代码块里的情况，自动提取 `{...}` 内容
- 兼容 `{` 前有换行/空白的情况
- 解析失败返回 `null`（**不再抛错打断游戏**），进入重试或降级流程

**第 4 层 · 自动重试（解析失败救回）**

首次解析失败时，用**精简提示词**重试一次：

```text
精简重试提示词 = JSON 格式模板 + 玩家状态 + 上一回合玩家行动
（不带冗长的 history，降低模型被历史纯文本"带偏"的概率）
```

实测：重试成功率 **100%**，绝大多数格式问题在重试后即恢复正常。

**第 5 层 · 降级兜底（永不卡死）**

重试仍失败（模型固执输出纯文本）时，直接把纯文本当作剧情接续，**不打断游戏**。前端用隐晦的游戏内语言过渡（如"命运之线悄然转动"），玩家感知不到技术细节，仅当轮次没有推荐选项和数值变化。

**状态兜底（贯穿第 3-5 层）**：`normalizeDelta` + `applyDelta` 做数值规范化与钳制——HP 钳制 `[0, maxHp]`、金币不为负、背包上限 20、升级/死亡规则由后端强制执行。**即使 AI 返回异常数值，游戏状态也不会崩坏。**

> **五层防护的意义**：提示词"引导" → 参数"要求" → 解析"容错" → 重试"救回" → 降级"兜底"。每一层都为下一层的失效做准备，保证极端情况下游戏依然可玩。

### 2.6 关键知识点（踩坑总结）

1. **`response_format: json_object` 是软约束**：OpenAI 兼容接口的标准参数，但部分模型未真正实现。若需要硬约束，需换支持严格 JSON 模式的服务/模型。且使用时要确保提示词中包含 "json" 关键字与格式示例（官方要求）。
2. **sensenova 思考模式默认开启**：`reasoning_effort` 默认 `high`，思考内容与输出**共享 max_tokens 配额**。长剧情下配额被思考吃光 → `finish_reason: length` → 输出为空。解法：设 `reasoning_effort: "none"` 并提高 `max_tokens`。
3. **`thinking` 字段不等于 `reasoning_effort`**：部分文档提到的 `thinking: "disabled"` 在 sensenova 上**不受支持**（返回 HTTP 400）。关闭思考请用 `reasoning_effort: "none"`。
4. **测试必须模拟真实用户**：发"继续推进冒险N"这种无意义指令会让模型困惑，且降级产生的纯文本写回 history 会污染上下文、诱使模型模仿输出纯文本。应**读取 AI 返回的 choices 并选择其一继续**。
5. **降级文本要"隐晦"**：不要向玩家展示"AI 未按格式返回"等技术信息，用游戏内语言包装，保持沉浸感。
6. **物品移动必须是代码级硬约束**：提示词是软约束，模型仍会"演绎"剧情而擅自移动物品。因此把 `removeInventory` / `weapon` / `armor` 在 `normalizeDelta` 中**直接丢弃**，把物品移动权限完全收归前端按钮。

# 第一部分：现有游戏的可玩性提升方案

## 1.1 大世界模式：从『无限对话』到『有目标的世界』

### 现状诊断

大世界模式的核心体验是自由输入 + AI 即时响应，但存在文字冒险类游戏的通病：

| 问题 | 表现 | 根源 |
|------|------|------|
| 目标感缺失 | 玩久了不知道『我在干嘛』 | 没有长线目标系统，剧情是碎片化的即时生成 |
| 数值成长单薄 | 升级回血之外，数值对玩法影响小 | 数值系统与战斗/探索的耦合弱 |
| 世界记忆有限 | NPC 对早期事件的记忆随轮次稀释 | 历史裁剪（trimHistory）为控制 token 成本 |

### 提升方案（按投入产出比排序）

**方案 A：任务/目标系统（推荐优先做）**

- **内容**：AI 世界观生成时同步生成 2~3 条长线任务链（主线 + 支线），任务有阶段目标与完成条件，由程序跟踪进度（不依赖 AI 记忆）；
- **为什么有效**：目标感是留存的第一驱动力。玩家『为了完成任务』会主动探索，而不是漫无目的地输入；
- **实现要点**：任务状态存入存档对象（现有 JSON 存档结构天然支持）；任务进度判定用程序规则 + AI 判定双轨（关键节点程序判定，模糊节点 AI 判定）；
- **成本估计**：中等——需要扩展世界观 schema、提示词与前端任务面板，约等于探案模式案件引擎的 60% 工作量。

**方案 B：NPC 关系与声望系统**

- **内容**：每个 NPC 维护对玩家的好感度/敌意值，影响对话态度、情报提供意愿、价格；关键 NPC 之间也有关系网（帮派、家族）；
- **为什么有效**：让世界『活』起来——玩家的行为有了涟漪效应，同一世界重玩体验不同；
- **实现要点**：关系值由程序结算（对话选项、赠礼、任务行为触发增减），注入 AI 提示词影响演绎风格；
- **成本估计**：中等——数据结构简单，难在提示词工程让 AI 稳定体现关系差异。

**方案 C：随机事件与奇遇系统**

- **内容**：探索/移动时按概率触发程序化事件（遭遇战、商队、遗迹发现、NPC 求助），事件由模板 + AI 润色生成；
- **为什么有效**：打破『输入-响应』的单调节奏，制造惊喜与风险；
- **成本估计**：低——事件模板库 + 概率触发器，纯增量开发不动现有逻辑。

**方案 D：多结局与世界状态快照**

- **内容**：重大选择导致世界状态分叉（城镇被毁/繁荣），结局由关键决策链决定，终局生成『你的传奇』总结；
- **为什么有效**：给重玩一个理由——不同选择路线看到不同世界；
- **成本估计**：中高——需要世界级状态跟踪与结局判定逻辑。

## 1.2 探案模式：从『找凶手』到『推理体验』

### 现状诊断

探案模式已有完整的案件引擎（真相 schema、物证击破、指认对质），完成度高。短板在：

- **难度曲线单一**：每局案件复杂度相近，缺少新手引导局与高难局；
- **推理工具少**：玩家只能靠脑记线索，缺少笔记/推理板辅助；
- **重复感**：题材固定五种，案件结构相似。

### 提升方案

**方案 A：难度分级与案件规模参数化**

- 案件生成时按难度档位控制：嫌疑人数（3~6）、说谎者数量、物证与关键线索的覆盖密度、误导线索比例；
- **为什么有效**：新手有成就感，老手有挑战，覆盖更广玩家群；
- **成本估计**：低——案件 schema 加参数，提示词按档位调整。

**方案 B：玩家推理笔记与排除板**

- 前端提供嫌疑人卡片墙：玩家可给每人标注怀疑度、排除理由、关联线索；终局与真相比对评分；
- **为什么有效**：推理游戏的『过程乐趣』可视化，类似推理杀的玩家标记系统（已有实现经验可复用）；
- **成本估计**：低——纯前端功能，参照推理杀标记的 localStorage 方案。

**方案 C：动态案件（凶手会行动）**

- 案件有时限轮次：玩家调查期间凶手会销毁证据、转移物证、甚至二次作案产生新线索；
- **为什么有效**：紧迫感 + 动态博弈，把静态解谜变成与凶手的赛跑；
- **成本估计**：高——需要案件状态机与 AI 驱动的凶手行为逻辑，是探案模式的质变级升级。

**方案 D：连环案/系列案**

- 一个存档内多起关联案件，前案的线索影响后案，最终拼出大真相；
- **成本估计**：高——跨案件状态管理复杂。

## 1.3 狼人杀模式：从『单机陪玩』到『博弈深度』

### 现状诊断

5 人局单人狼人杀已完成基础闭环，但 AI 博弈深度不足：

- AI 发言策略相对固定（狼人伪装/预言家报验人/村民推理），缺少基于局势的动态策略；
- 单局时长短，玩家成长感弱。

### 提升方案

**方案 A：AI 策略人格化**

- 每个 AI 玩家随机分配策略人格：激进型（强指认）、谨慎型（跟风）、分析型（逻辑链发言）、情绪型（容易被带节奏）；
- **为什么有效**：每局对手『性格』不同，博弈体验多样化，玩家需要识人；
- **成本估计**：低——人格参数注入提示词即可。

**方案 B：进阶板子与特殊角色**

- 增加守卫、女巫、猎人等角色（推理杀的多技能夜晚结算引擎可直接复用——这是现成的技术资产）；
- **成本估计**：低~中——结算逻辑有推理杀的成熟实现可移植。

**方案 C：赛季积分与段位**

- 胜负记录、连胜奖励、段位徽章存入账号体系（users 表扩展）；
- **为什么有效**：给单机玩法注入长线目标；
- **成本估计**：低。

## 1.4 推理杀模式：打磨最成熟的核心资产

### 现状诊断

推理杀是本项目完成度与打磨度最高的模式（结构化发言三层架构、8 局验证、三幕演出动画、关系图复盘）。剩余提升空间：

- **板子多样性**：目前固定 7 人标准/10 人进阶两套，角色池组合变化有限；
- **法官参与感**：法官是纯观察者，白天阶段交互较少（只有听取发言与裁决）；
- **难度可选**：AI 发言质量高时对新手推理压力大。

### 提升方案

**方案 A：自定义板子编辑器**

- 玩家自选角色组合（从 17 角色池挑选）、人数（6~12）、阵营配比，生成自定义局；
- **为什么有效**：玩家创造玩法（如『全中立局』『无狼人推理局』），UGC 延长生命周期；
- **成本估计**：中——角色池数据已有，需要组合合法性校验与平衡性提示。

**方案 B：法官质询机制**

- 白天阶段法官可对单个角色发起质询（追问细节），AI 必须基于知识包应答，说谎者有概率露破绽；
- **为什么有效**：把法官从旁观者变成审讯官，参与感大增；质询次数有限（如每天 2 次）保持平衡；
- **成本估计**：中——质询提示词 + 应答校验（复用现有结构化发言校验框架）。

**方案 C：难度分级**

- 简单局：AI 发言含更多可推理的破绽；困难局：伪装更严密、线索更稀疏；
- **成本估计**：低——提示词参数化。

**方案 D：连续剧情（村庄编年史）**

- 多局之间延续：上局存活角色进入下局、恩怨关系影响发言倾向；
- **成本估计**：高——跨局状态与叙事连续性管理。

# 第二部分：新增文字游戏的可行性评估

## 可行性总论

**结论：高度可行，且是当前架构下性价比最高的发展方向。**

依据：
1. **架构即为此设计**——可插拔模式注册表（MODES 表 + 统一接口 newGame/handleAction/snapshot）意味着新增模式 = 新增一个文件 + 注册，路由/存档/账号/前端框架零改动；
2. **技术栈完全匹配**——文字游戏的全部需求（状态管理、LLM 调用、结构化输出校验、存档）都是现有能力的重复使用；
3. **有成熟范式可循**——推理杀的『程序结算事实 + AI 演绎措辞』三层架构已被验证，可直接套用到任何新文字游戏。

## 候选游戏评估（按推荐度排序）

### 2.1 🏰 模拟经营：文字王国（推荐度 ★★★★★）

**玩法概述**：玩家扮演领主，每回合做出经营决策（建设、征税、外交、招募），AI 生成事件与臣民反应，程序结算资源与国力，目标是在随机危机（天灾、战争、叛乱）中存活并繁荣。

**为什么好玩**：
- **决策密度高**：每回合 3~5 个有意义的抉择，比冒险模式的自由输入更聚焦；
- **随机事件制造叙事**：AI 生成的事件（『边境领主请求联姻』『商队带来瘟疫传闻』）让每局故事独一无二；
- **长线成长**：王国从村庄到帝国的可视化成长曲线，天然的多周目动力；
- **失败也有故事**：王国覆灭时生成编年史总结（类似推理杀的终局复盘）。

**实现要点**：
- 状态：资源（金币/粮食/民心/兵力）+ 建筑 + 随机事件队列，全部程序结算；
- AI 职责：事件文本生成、臣民 NPC 反应演绎、结局叙事——**不碰数值**（沿用推理杀的确定性原则）；
- 前端：资源面板 + 决策卡片 + 事件流，复用现有弹窗/抽屉组件体系；
- **成本估计**：与推理杀初期版本相当（2~3 周打磨到可玩）。

### 2.2 🎭 剧情互动小说：多结局分支叙事（推荐度 ★★★★☆）

**玩法概述**：AI 生成一部多角色互动小说（悬疑/宫斗/科幻题材），玩家扮演主角做关键抉择，剧情分支由程序跟踪，结局由选择链决定。

**为什么好玩**：
- 情感沉浸是文字媒介的强项——比游戏性更打动人的是故事；
- 多结局驱动重玩（『如果当时选另一个人会怎样』）；
- 开发成本在文字游戏里最低（无复杂结算逻辑）。

**实现要点**：
- 分支管理是核心难点：AI 生成剧情时需输出结构化的分支标记（选项 → 分支 ID），程序跟踪当前分支与关键抉择记录；
- 需要防止剧情漂移：关键事实（人物生死、关系变化）由程序记录并注入提示词；
- **成本估计**：低~中，主要工作量在提示词工程与分支校验。

### 2.3 🕵️ 密室解谜：文字逃脱（推荐度 ★★★★☆）

**玩法概述**：AI 生成一个密室场景（房间、物品、谜题链），玩家通过文字指令探索、组合物品、解谜，限时逃脱。

**为什么好玩**：
- 谜题的『顿悟感』是强多巴胺来源；
- 单局时长短（15~30 分钟），适合碎片时间，与现有长局模式形成互补；
- 谜题链结构（A 解开才能碰 B）天然适合程序验证。

**实现要点**：
- 谜题与物品状态由程序管理（物品位置、已解谜题、锁状态），AI 只负责场景描述与氛围；
- 谜题生成质量是关键：需要设计谜题模板库（密码锁、图案、逻辑推理）让 AI 填充参数，纯 AI 原创谜题容易无解或不合理；
- **成本估计**：中——谜题模板库设计需要巧思。

### 2.4 ⚔️ 文字 Roguelike 地牢爬行（推荐度 ★★★☆☆）

**玩法概述**：程序生成地牢（房间/怪物/宝物），回合制文字战斗，死亡即重来，局间解锁永久成长。

**为什么好玩**：
- Roguelike 的『一局一世界 + 死亡惩罚 + 局外成长』是被验证百次的成瘾循环；
- 随机性带来无限重玩。

**实现要点**：
- 战斗/地图/掉落全部程序结算（AI 只做战斗描述润色）——工作量集中在数值系统；
- 与大世界模式的战斗系统有重叠，可部分复用；
- **成本估计**：中高——数值平衡需要大量测试迭代。

### 2.5 🎲 文字派对游戏：你画我猜/故事接龙（推荐度 ★★☆☆☆）

**玩法概述**：轻量休闲——AI 出题猜词、多人故事接龙（当前单账号体系下需先支持本地多人轮换）。

**评估**：趣味性依赖多人场景，与当前单账号架构匹配度低，暂不推荐。

# 第三部分：新增 2D/3D 游戏的可行性评估

## 3.1 先明确『华丽 2D/3D』意味着什么

| 类型 | 技术需求 | 与现有架构的关系 |
|------|----------|------------------|
| 2D 网页小游戏（Canvas/PixiJS） | 前端渲染引擎 + 游戏循环 | 前端新增渲染层，后端基本复用 |
| 3D 网页游戏（Three.js/WebGL） | 3D 引擎 + 模型/材质资源 + 光照 | 前端重写渲染层，资源管线全新 |
| 高品质 3D（接近原生画质） | 高级渲染（PBR/后处理）+ 大量美术资源 | 远超当前项目体量 |

## 3.2 可行性逐层分析

### 层次一：轻量 2D 可视化增强（可行性：★★★★☆ 高）

**范围**：为现有文字游戏添加 2D 视觉层——不是独立 2D 游戏，而是让文字游戏『看得见』：

- 探案模式：场景地图（2D 平面图，点击房间移动）、人物头像立绘、物证图标；
- 推理杀：关系图的动态化（现有 SVG 关系图升级为可交互力导向图）；
- 大世界：文字配插画（AI 文生图 API 生成场景图）；
- 模拟经营（若做）：资源图表、王国俯视图。

**为什么可行**：
- Vue 组件体系与 Canvas/SVG 渲染可共存（现有关系图就是 SVG）；
- AI 文生图 API（如 DALL·E/Stable Diffusion 兼容接口）与现有 LLM 调用架构同构——都是 HTTP API 封装；
- 不需要游戏循环（无实时渲染压力），性能无虞。

**成本估计**：每个可视化增强点 1~3 天，渐进式投入。

**风险**：AI 生图的成本（每张图约等于数百次文字 token 的费用）与风格一致性（需固定风格提示词）。

### 层次二：独立 2D 小游戏（可行性：★★★☆☆ 中）

**范围**：真正的 2D 游戏——如卡牌对战（可视化卡面）、棋类（AI 对手）、2D 地牢（像素风）。

**技术路径**：
- 渲染：PixiJS 或原生 Canvas（Vue 生态内嵌一个游戏画布组件）；
- 逻辑：游戏规则程序结算（现有引擎模式），AI 负责对手策略或叙事；
- 资源：像素风/矢量风美术（可用开源素材库或 AI 生图）。

**为什么有可行性**：
- 卡牌/棋类的规则引擎与推理杀的确定性结算同构——本质都是状态机；
- AI 对手可以复用 LLM（策略提示词）或纯算法（棋类 minimax）。

**主要障碍**：
- **游戏循环与 Vue 的整合**：实时渲染需要 requestAnimationFrame 循环，与 Vue 响应式的整合需要架构调整（游戏画布作为独立组件，状态单向同步）；
- **美术资源管线**：当前项目零美术资产，需要建立素材管理；
- **开发范式转变**：从『表单+文本流』到『实时交互』，前端复杂度上一个数量级。

**成本估计**：一个可玩的 2D 卡牌对战约 3~4 周（含美术）；像素地牢 6~8 周。

### 层次三：3D 游戏（可行性：★★☆☆☆ 低，但非零）

**范围**：Three.js/WebGL 的 3D 场景游戏。

**技术上可行的部分**：
- Three.js 成熟且与 Vue 可集成（vue-three 相关方案）；
- 简单 3D 场景（低多边形风格 Low-Poly）对模型量要求低，开源模型库（如 Kenney）可商用；
- 3D 文字冒险（3D 场景探索 + 文字交互）是折中形态——3D 提供空间感，文字保留叙事深度。

**主要障碍（按严重度排序）**：
1. **移动端性能**：手机浏览器跑 3D 需要严格优化（低面数、无复杂光照），本项目手机端是主要游玩场景；
2. **资源体积**：3D 模型+纹理动辄数十 MB，与当前『160KB JS 包』的轻量哲学冲突，首屏体验倒退；
3. **开发技能跨度**：3D 开发（场景/相机/光照/碰撞）与当前全栈文字开发是不同技能域，学习曲线陡峭；
4. **投入产出比**：3D 的视觉收益对『文字冒险』核心用户群的边际价值存疑——玩文字游戏的人要的是叙事与推理，不是画面。

**成本估计**：最简 3D 探索 demo 4~6 周；可发布品质的 3D 游戏 3 个月起，且需要持续美术投入。

## 3.3 2D/3D 方向的结论

**不建议现在做独立 2D/3D 游戏**，理由：
1. 项目核心竞争力是『LLM 驱动的叙事与推理』——这是文字游戏的护城河，视觉游戏赛道竞争激烈且无差异化优势；
2. 当前用户（您自己+测试玩家）的反馈全部集中在玩法与体验，无一涉及视觉升级诉求；
3. 轻量 2D 可视化增强（层次一）能以 1/20 的成本获得 80% 的『华丽感』提升——这是正确的性价比选择。

**若未来要做，推荐路径**：文字游戏成熟 → 2D 可视化增强（积累渲染经验）→ 3D 文字冒险（Low-Poly + 空间探索）→ 独立视觉游戏。每一步都可回退，不押注。

|------|-------------|-------------|-----------|

## 推荐路线图

**近期（性价比最高组合）**：
1. 推理杀·法官质询机制（强化最成熟资产）+ 难度分级；
2. 探案·推理笔记板（复用推理杀标记经验，纯前端）；
3. 大世界·任务系统（解决目标感缺失）。

**中期**：
4. 新增模拟经营『文字王国』（新玩家群 + 架构验证）；
5. 狼人杀进阶板子（复用推理杀结算引擎）；
6. 2D 可视化增强第一批（探案场景图 + AI 插画）。

**远期（视效果决定）**：
7. 互动小说 / 密室解谜模式；
8. 大世界 NPC 关系网与多结局；
9. 3D 文字冒险（若 2D 增强反响好）。

## 一个贯穿性的原则

本项目所有成功功能（结构化发言、确定性结算、弹窗时序、关系图）都遵循同一原则：**程序管事实，AI 管表达**。任何新玩法设计都应先回答：『哪些是必须程序结算的事实？哪些可以交给 AI 演绎？』——这个分界画对了，游戏就稳了。
