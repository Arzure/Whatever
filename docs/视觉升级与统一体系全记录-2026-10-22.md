# 第二章 盒模型：一个内边距引发的血案

## 2.1 导言

下午，推理杀游戏界面出现诡异换行：侧栏里『法官』两个字竖着排成一字一行，『主菜单』按钮断成『主菜』『单』两行。这个 bug 的根因只有一行 CSS，但它背后是前端最基础也最重要的概念——**盒模型**。

## 2.2 概念：盒模型

浏览器把每个元素画成一个矩形盒子，从内到外分四层：

```
┌──────────────── margin（外边距：盒子之间的距离）
│ ┌────────────── border（边框）
│ │ ┌──────────── padding（内边距：内容与边框之间的空隙）
│ │ │ ┌────────── content（内容：文字、图片）
│ │ │ │
│ │ │ └──────────
│ │ └────────────
│ └──────────────
└────────────────
```

**padding 决定了内容与边框之间留多少空隙**。它和 width 的关系是：内容区宽度 = 盒子宽度 − 左右 padding − 左右边框。也就是说，**左右 padding 越大，留给文字的空间越窄**。

## 2.3 语法：padding 简写规则

CSS 允许 padding 写 1~4 个值，规则如下：

| 写法 | 含义 | 记忆方法 |
|---|---|---|
| `padding: 10px` | **四个边**都是 10px | 一个值管全部 |
| `padding: 10px 20px` | 上下 10px，左右 20px | 先上下，后左右 |
| `padding: 10px 20px 30px` | 上 10px，左右 20px，下 30px | 上、左右、下 |
| `padding: 1px 2px 3px 4px` | 上右下左（顺时针） | 像时钟转一圈 |

## 2.4 案例复盘

**事故代码**：

```css
.side-panel {
  width: 280px;
  padding: calc(var(--bar-h, 48px) + 16px); /* ← 事故现场 */
}
```

这行代码的本意是：顶栏悬浮后，侧栏顶部要额外让出顶栏的高度（约 48px + 原有 16px）。但它是**单值简写**——64px 被同时加到了**四个边**。

**算一笔账**：侧栏总宽 280px，左右各吃掉 64px，内容区只剩 280 − 128 = **152px**。中文字符 14px 字号下每个字约占 14px，152px 只够放约 10 个字——但侧栏里还有头像、边距、按钮内边距，实际留给『法官』两个字的宽度不足一个字，于是每个字被迫独占一行。

**修复代码**：

```css
.side-panel {
  width: 280px;
  padding: calc(var(--bar-h, 48px) + 16px) 16px 16px; /* 上、左右、下 */
}
```

三值写法：顶部让位 64px，左右和底部恢复原有 16px。四个视图共八处同类错误全部修复。

## 2.5 小结

1. padding 单值简写作用于四边，『只想改一边』时永远不要用它；
2. 排查布局挤压问题时，先算内容区实际宽度 = 总宽 − 左右 padding − 左右边框；
3. `calc()` 可以在 CSS 里做算术，常用于『原有间距 + 动态让位高度』的组合。

# 第三章 层叠上下文：谁在上面，谁在下面

## 3.1 导言

顶栏改成固定悬浮（详见第四章）后，一个新问题浮现：如果某个弹窗的层级低于顶栏，它会被顶栏压住一角。这涉及 CSS 的**层叠上下文**概念。

## 3.2 概念：z-index 与层叠顺序

屏幕是二维的，但元素之间存在前后遮挡关系，构成第三维。`z-index` 就是这一维的坐标：**数字越大越靠上层**。规则要点：

1. `z-index` 只对 `position` 不是 static 的元素（如 fixed、absolute）生效；
2. 同层级比较中，z-index 大者胜；
3. 常见约定：背景 0 → 普通内容 1~10 → 固定顶栏 70 → 抽屉/弹窗 90~100 → 全局遮罩 200+。

## 3.3 案例复盘：全站层级审计

顶栏固定悬浮后 z-index 为 70。走查时审计全站弹窗层级：

| 元素 | z-index | 是否高于顶栏 | 结论 |
|---|---|---|---|
| 推理杀移动端抽屉 | 95 | 是 | 正常 |
| 终局弹窗 | 90 | 是 | 正常 |
| 绘图全屏预览 | 200 | 是 | 正常 |
| 访问门（登录拦截） | 9999 | 是 | 正常 |
| 底部栏 / 移动 dock | 30~50 | 否 | 位于屏幕底部，与顶栏无交集，正常 |

审计方法：`grep -rn 'z-index' components/*.vue` 列出全部层级声明，逐一与顶栏比较。

## 3.4 小结

1. 引入新的固定悬浮元素时，必须全站审计 z-index，否则会出现『弹窗被顶栏压住』的诡异现象；
2. 层级数字要成体系（个位内容、十位悬浮栏、百位弹窗、千位全局门），不要随手写；
3. z-index 低于顶栏不一定是错——关键看两者在屏幕上是否有交集区域。

# 第四章 毛玻璃效果：三次失败换来的正确答案

## 4.1 导言

毛玻璃（frosted glass / glassmorphism）是近年流行的界面质感：元素半透明，背后的内容透过来时被磨砂模糊。本章记录了让顶栏毛玻璃从『完全看不见』到『肉眼可见』的三次失败与最终答案——这是全书最有教学价值的一章。

## 4.2 概念：backdrop-filter

```css
.app-bar {
  background: rgba(19, 26, 46, 0.55);      /* 半透明底色 */
  backdrop-filter: blur(24px) saturate(1.6); /* 背后内容模糊+提饱和 */
}
```

- `blur(24px)`：把元素**背后**的内容模糊 24 像素半径；
- `saturate(1.6)`：把模糊后的颜色饱和度提升到 1.6 倍，避免模糊后发灰；
- 底色不透明度决定『透出多少背后的内容』：0.55 表示 55% 底色 + 45% 背后内容。

**关键认知**：backdrop-filter 模糊的是『元素背后正在经过的东西』。如果背后永远只有一块纯色背景，模糊纯色 = 什么都没发生。

## 4.3 第一次失败：毛玻璃完全看不见

**现象**：代码正确，效果为零。

**根因**：顶栏原本是普通文档流元素（随内容从上往下排），而页面滚动发生在下方视图的内部容器里——**内容永远不会从顶栏底下穿过**。顶栏背后只有页面纯色背景，模糊纯色毫无视觉变化。

**修复**：顶栏改为 `position: fixed`（固定悬浮在屏幕顶部，不随页面滚动），内容从它底下穿过，滚动时文字卡片从毛玻璃后掠过被实时模糊。

```css
.app-bar {
  position: fixed;
  top: 0; left: 0; right: 0;
  z-index: 70;
}
```

## 4.4 第二次失败：内容被顶栏挡住

顶栏悬浮后，页面最顶部的内容被它盖住了。需要给内容让出顶栏高度。

**方案**：用 ResizeObserver（浏览器提供的元素尺寸监听器）把顶栏实际高度写入 CSS 变量，各视图滚动容器引用该变量让位：

```js
watch(barEl, (el) => {
  if (!el) return;
  const syncBarH = () =>
    document.documentElement.style.setProperty('--bar-h', el.offsetHeight + 'px');
  syncBarH();
  new ResizeObserver(syncBarH).observe(el);
});
```

```css
.messages {
  padding: calc(var(--bar-h, 48px) + 24px) 28px 24px; /* 顶部让位 */
}
```

**为什么用 ResizeObserver 而不是写死 48px**：手机窄屏上顶栏按钮会换行，高度会变。监听器保证让位高度始终等于顶栏实际高度。

**为什么用 watch 而不是在 onMounted 里直接读**：顶栏在登录成功后才渲染，挂载时它还不存在。watch 顶栏的模板引用，它一出现就建立同步。

## 4.5 第三次失败：让位加错了地方

让位内边距最初加在**内容区**（.app-body）上——结果滚动容器的顶边永远在顶栏下方，内容又不从顶栏底下穿过了，毛玻璃再次失效。

**正确位置**：让位内边距必须加在**各视图自己的滚动容器**上。原理：内边距属于滚动区域的一部分，滚动时内容会穿过内边距区域——也就是穿过顶栏后方。

```
错误：内容区 padding-top → 滚动容器整体下移 → 顶栏背后无内容
正确：滚动容器 padding-top → 滚动内容穿过让位区 → 顶栏背后有内容掠过
```

## 4.6 深浅主题的毛玻璃差异（原理篇）

**现象**：深色主题毛玻璃效果很好，浅色主题几乎看不见。

**原理**：毛玻璃的可见度 = 背后内容与底色的**对比度**。

- 深色模式：浅色文字卡片从深色顶栏后穿过 → 明暗对比强烈 → 模糊醒目；
- 浅色模式：白底卡片从白色顶栏后穿过 → 白上加白 → 模糊了也看不出来。

这是浅色主题做毛玻璃的**普遍难点**，不是实现错误。macOS 浅色模式的毛玻璃同样偏微妙。

**最终定稿参数**（经七轮反馈迭代）：

| 主题 | 底色不透明度 | 模糊 | 说明 |
|---|---|---|---|
| 深色 | 0.55 | blur(24px) saturate(1.6) | 效果好，定稿 |
| 浅色 | 0.15 | 同深色 | 底色调到很透才可见；模糊单独加强版试过一轮，按反馈回退 |

## 4.7 附属功能：滚动阴影

顶栏加了 `.scrolled` 状态类：页面任何滚动容器滚过 8px 后，顶栏底部阴影渐显，强化悬浮层次。

```js
document.addEventListener('scroll', onAnyScroll, true); // 第三个参数 true = 捕获阶段
```

**知识点——事件捕获**：滚动事件默认只发给发生滚动的那个容器。第三个参数传 true 后，监听挂在 document 上也能捕捉到**任何内部容器**的滚动——因为捕获阶段事件会从外向内传播，路过 document。

## 4.8 小结

1. backdrop-filter 的前提：背后必须有内容经过 → 元素必须 fixed/absolute 悬浮；
2. 悬浮后必须让位，让位加在滚动容器上而不是外层容器上；
3. 让位高度用 CSS 变量 + ResizeObserver 动态同步；
4. 浅色主题毛玻璃天然弱，靠降低底色不透明度弥补；
5. 视觉参数的最终标准是用户主观感受，不合适就干净回退。

# 第五章 主题系统：一套代码，两副面孔

## 5.1 导言

项目支持深色（定稿）与浅色两套主题。当天核实发现浅色主题早已通过提交 44fe90e 完整入库——这里借它讲解主题系统的实现原理。

## 5.2 概念：CSS 变量

```css
:root {
  --bg: #131c3a;      /* 深色：背景 */
  --panel: #1e2a52;   /* 深色：面板 */
}
html.light {
  --bg: #f6f8fc;      /* 浅色：同一批变量换值 */
  --panel: #ffffff;
}
.panel {
  background: var(--panel); /* 引用变量，主题切换自动变色 */
}
```

CSS 变量（`--名字`）是**一处定义、处处引用**的自定义值。深浅主题共用一套变量名，只在 `html.light` 下换一套值——所有引用变量的元素自动切换，这就是主题系统的全部原理。

## 5.3 主题切换的实现

```js
const theme = ref(localStorage.getItem('theme') === 'light' ? 'light' : 'dark');
function applyTheme() {
  document.documentElement.classList.toggle('light', theme.value === 'light');
}
```

三步：读 localStorage（刷新后保持）→ 给 `<html>` 加/删 light 类 → CSS 变量块自动生效。

## 5.4 图标如何适配主题：currentColor

统一图标组件（第七章）的 SVG 线条写 `stroke="currentColor"`——线条颜色自动继承所在元素的文字颜色。文字是深色主题的浅色，图标就是浅色；切到浅色主题文字变深，图标跟着变深。**零额外代码实现主题适配**。

## 5.5 小结

1. 主题系统 = CSS 变量 + 根元素类名切换 + localStorage 持久化；
2. 组件永远引用变量而不是硬编码颜色，硬编码是主题适配的头号敌人；
3. currentColor 让 SVG 图标免费获得主题适配能力。

# 第六章 动效设计：让界面活起来

## 6.1 导言

对标 reactbits.dev、animata.design 等动效组件库的设计语言：**交互驱动的动效**——动效是操作的反馈，不是静态装饰。当天为四个游戏视图（侦探/狼人杀/世界/推理杀）实施了三项动效。

## 6.2 概念：CSS 动画三要素

```css
.msg {
  animation: msg-in 0.32s ease both;
}
@keyframes msg-in {
  from { opacity: 0; transform: translateY(10px); }
  to   { opacity: 1; transform: none; }
}
```

- `@keyframes`：定义动画的两个关键帧（从透明+下移 10px，到完全显示）；
- `0.32s ease`：时长与缓动曲线，ease 是先快后慢，观感自然；
- `both`：动画前后都应用关键帧样式，防止闪跳。

## 6.3 三项动效实现

**① 消息入场动画**：新消息淡入 + 上移（上面的代码），让每条发言的到达都有可感知的反馈。

**② 按钮微交互**：

```css
.btn:hover:not(:disabled) { transform: translateY(-1px); filter: brightness(1.1); }
.btn:active:not(:disabled) { transform: scale(0.96); }
```

悬停上浮 1px + 提亮 10%（提示可点），按下缩到 96%（模拟物理按压）。`:not(:disabled)` 保证禁用按钮无反馈。

**③ 阶段标题动画**：阶段徽章（如『第 N 夜』）切换时字距从 0.45em 收拢到正常并淡入，强化昼夜交替的仪式感。

**技巧——用 :key 重播动画**：CSS 动画只在元素首次渲染时播放一次。给徽章加 `:key="phase"`，阶段一变，Vue 认为这是新元素、销毁重建，动画自动重播。

## 6.4 动效设计三原则

1. **反馈优先**：动效首先服务于操作反馈（消息到达、按钮按压），其次才是装饰；
2. **短促克制**：入场 0.3 秒上下，微交互 0.1 秒上下——超过 0.5 秒的界面动效会让人烦；
3. **全站一致**：同类交互用同一种动效，混用多种风格比没有动效更糟。

## 6.5 小结

1. @keyframes + animation 是 CSS 动画的基本功；
2. hover/active 微交互是性价比最高的动效；
3. :key 变化触发元素重建，是重播动画的标准手法；
4. 动效时长宁短勿长。

# 第七章 组件化思维：从 101 个图标到 1 个组件

## 7.1 导言

全站约 101 处 emoji 当图标用（🏠 📂 ☀️…），按钮样式分散在 12 个文件共 83 处定义。本章讲述两次重构：统一图标体系与统一按钮体系。

## 7.2 问题：为什么 emoji 当图标不好

1. **渲染不可控**：同一 emoji 在 Windows/macOS/Android 上长得完全不同；
2. **颜色不可控**：emoji 是彩色图片，无法跟随深浅主题变色；
3. **大小不可控**：无法精确对齐文字基线，混排时忽高忽低。

## 7.3 方案：统一图标组件

新建 `Icon.vue`：内联 SVG 线性图标（stroke 1.5px、圆角端点、24×24 网格），内置 26 个图标，`currentColor` 继承文字颜色，零外部依赖。

```vue
<Icon name="home" /> 首页
<Icon :name="theme === 'light' ? 'moon' : 'sun'" />
```

**替换范围（31 处界面操作图标）**：顶栏全部按钮、首页入口卡片、办公页 7 个标签页、绘图工作台模式切换、各处关闭与删除按钮。

**保留不动（约 40 处）**：游戏内容性 emoji（消息文本里的 💀、终局谢幕）——它们是**游戏叙事表达**，不是界面图标。区分标准：出现在界面控件上的是图标，出现在内容文本里的是表达。

## 7.4 方案：统一按钮体系

**问题**：各视图按钮各写各的——内边距两种、字号两种、冒险页主按钮配色还偏离体系。

**方案**：全局建立四层级体系：

| 层级 | 类名 | 视觉 | 使用场景 |
|---|---|---|---|
| 主按钮 | `.btn.primary` | 主题色渐变填充 | 每屏最多一个的核心操作 |
| 危险按钮 | `.btn.danger` | 红色渐变 | 删除、处刑等不可逆操作 |
| 幽灵按钮 | `.btn.ghost` | 透明底 + 描边 | 次要操作 |
| 通栏修饰 | `.btn.full` | 占满整行 | 可与上面任意组合 |

六个视图 42 处重复定义全部删除，收敛到全局（净减 132 行）。

## 7.5 关键知识点：scoped 样式优先级

Vue 的 `<style scoped>` 会给选择器加上属性限定（如 `.btn[data-v-xxx]`），**优先级高于全局同名选择器**。因此统一体系不能只加全局样式——**必须删掉各视图的旧定义**，否则旧样式会继续覆盖，统一形同虚设。这是本次重构中最容易踩的坑。

## 7.6 组件化的收益公式

```
N 处重复定义 → 1 处统一定义
修改成本：N 次 → 1 次
不一致风险：N 种 → 0 种
```

## 7.7 小结

1. 界面图标用 SVG 组件，内容表达可保留 emoji，区分标准是『控件还是内容』；
2. currentColor 让图标免费获得主题适配；
3. scoped 样式优先级高于全局，统一体系必须删除旧定义；
4. 按钮分四层级，主按钮每屏最多一个。

# 第八章 工程方法论：如何确信代码真的没问题

## 8.1 导言

本章不是 CSS 知识，而是**工程判断方法**——当天多次用到，值得单独成章。

## 8.2 考古：判断工作做没做过

**问题**：凭记忆以为浅色主题还没做，实际早已入库。

**方法**：

```bash
git log -S 'html.light' -- frontend/src/style.css   # 哪个提交引入了这个字符串
git branch -r --contains 44fe90e                     # 这个提交推到远端了吗
```

`git log -S`（pickaxe）搜索『字符串的增删历史』，是定位『这个改动是谁引入的』的标准命令；`--contains` 检查提交是否已在某分支，是核实『推没推』的标准命令。

**原则**：判断做没做过，查仓库，不查记忆。

## 8.2 回归：改 A 坏 B 怎么办

毛玻璃改造（A）引入了诡异换行（B）。处理流程：

1. **定位**：从症状（一字一行）反推空间不足 → 检查宽度相关属性 → 找到 padding；
2. **修复**：只改错误的部分（简写改三值），不顺手重构无关代码；
3. **全量排查**：`grep -rn 'padding: calc'` 检查所有同类写法，四个视图八处一次修完——**修一处必须排查所有同类**，否则同样的 bug 会分批冒出来；
4. **提交信息写清根因**，方便未来考古。

## 8.3 走查：静态审计清单

大改动后的系统性检查：

| 检查项 | 方法 |
|---|---|
| 同类错误残留 | grep 全站同类写法 |
| 层级冲突 | grep z-index，与新增悬浮元素比较 |
| 动画冲突 | 检查新旧动画选择器是否重叠 |
| 产物完整性 | 构建产物中 grep 关键特征（类名/变量名） |
| 删除干净 | grep 已删功能的关键词，应为 0 |
| 服务状态 | pm2 list + curl 首页状态码 |

## 8.4 视觉验收标准

> 视觉类改动的验收标准是**肉眼可感知**，不是『色值变了』——深色底上微调色相等于没改。

- 每次视觉改动必须构建 + 重启 + 浏览器肉眼确认；
- 用户说『看不出变化』时，第一反应应是**怀疑实现路径错了**（如毛玻璃背后没内容），而不是加大参数；
- 参数调整保留快速微调能力，用户反馈『过了』就干净回退。

## 8.5 小结

1. 考古用 git log -S 和 --contains，不凭记忆；
2. 修一处 bug 必须全量排查同类写法；
3. 大改动后跑静态审计清单；
4. 视觉验收以肉眼可感知为准。
