# 1.4b 开发模式与生产模式的区别（小白版）

## 本机回环是什么

每台联网电脑有多个『网络接口』（多扇门）：
- **公网门**（如 124.220.208.156）：通向互联网，全世界能访问
- **本机回环门**（127.0.0.1，域名 localhost）：只通向自己——数据从本机发出绕一圈回到本机，永不出门

回环地址上的服务，外部设备**物理上无法访问**——不是防火墙拦截（可被绕过），而是网络层面无路径。这就是后端监听改回环后公网直连被彻底杜绝的原理。

## 两种模式对比

| | 开发模式（本机）| 生产模式（服务器）|
|---|---|---|
| 前端 | Vite 开发服务器（5173，热更新）| 构建静态文件由后端托管 |
| 后端监听 | 所有网卡 0.0.0.0（手机/同事可访问调试）| 仅回环 127.0.0.1（公网物理隔离）|
| 访问 | localhost:5173 | 公网 IP + HTTPS（Caddy 反代）|
| 数据 | 测试数据 | 真实用户账号/存档/图片 |
| 安全 | 宽松（方便优先）| 严格（口令+JWT+回环+限速）|
| 改代码 | 保存即生效 | 重新构建+重启 |

**监听地址决定『谁有可能访问』**：监听 0.0.0.0 时本机（localhost）、同 WiFi 手机、同事电脑都能访问——本机访问只是其中一种方式；监听 127.0.0.1 时只有本机自己。

## 代码如何区分

同一份代码靠环境变量（NODE_ENV）在启动时判断模式，选择对应行为（监听地址等）。HOST 变量可直接覆盖监听地址兜底。

## 环境变量注入方式与教训

生产环境变量由进程管理器（pm2 --update-env + save）注入，服务重启自动携带。**不要在终端 export 后一走了之**——终端变量影响会话内所有命令：曾因 export NODE_ENV=production 后安装 npm 包，npm 按生产模式主动移除了开发依赖（vite），导致构建失败且重装无效（环境变量仍在）。修复：npm install --include=dev。教训：终端临时变量用完即清；识别特征『装新库后构建工具消失+重装无效』→ 先查环境变量。

# 1.5 鉴权体系完整讲解（小白版）

本节讲清楚项目的三件安全资产：访问口令（ACCESS_TOKEN）、登录令牌（JWT）、签名密钥（JWT_SECRET）——它们是什么、怎么工作、如何配合。

## 1.5.1 JWT_SECRET：整个系统的『印章』

**来源**：项目代码自动生成（`server/auth.js` 启动时）：服务首次启动检查 .env，没有 JWT_SECRET 就用加密安全随机数生成 32 字节（64 位十六进制字符串），自动追加写入 .env——这样重启不换密钥（否则每次重启所有登录态和图片签名全部失效）。

**使用位置（共两处）**：
1. **登录令牌签发与验证**（auth.js）：登录成功后给令牌内容盖的章
2. **图片 URL 签名**（index.js 的 signDrawFile / verifyDrawFileSig）：给 `用户ID:文件名:过期时间` 算的 HMAC

**安全红线**：拿到它就能伪造任意用户的登录态和任意图片签名。所以 .env 绝不进 git（已确认从未提交）、绝不外泄。怀疑泄露时删掉 .env 里这行重启即换新（代价：所有用户需重新登录、24 小时内图片签名失效）。

## 1.5.2 登录全流程：从输密码到拿令牌

**第一步：密码验证（数据库不存密码原文）**

注册时服务器生成随机 32 字节『盐』（salt），用盐+密码算哈希，按 `盐:哈希` 格式存库。登录验证：按用户名查库取记录 → 用同一个盐+您输入的密码重算哈希 → 与库里的比对，一致即密码正确。

为什么这么绕：哈希是单向的，从哈希反推不出密码——数据库泄露攻击者拿到的只是指纹；每个用户盐不同，同样密码哈希也不同（防彩虹表批量破解）。

**第二步：签发令牌**

验证通过后，服务器用 JWT_SECRET 给 `{uid, username, 签发时间, 过期时间}` 盖章，生成三段式令牌放响应里发回：

```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOi...fQ.7f3a9b...",
  "user": { "id": "u_ccd20f57", "username": "pt43661" }
}
```

**第三步：前端保存**

令牌存浏览器 localStorage（`rpg_auth_token` 键）——浏览器给每个网站划的本地小仓库，关浏览器不丢。F12 → Application → Local Storage 可亲眼看到。之后每次请求自动放进 `Authorization: Bearer <令牌>` 头。

## 1.5.3 JWT 令牌长什么样：三段式拆解

```
第1段（头）:   eyJhbGciOiJIUzI1NiJ9        → 声明用 HMAC-SHA256 算法
第2段（内容）: eyJ1aWQiOi...              → base64 编码的 {uid, username, iat, exp}
第3段（签名）: 7f3a9b...                   → 用 JWT_SECRET 对前两段算的 HMAC
```

**关键认知**：
- 第 2 段只是 base64 **编码不是加密**——谁都能解开看，所以里面绝不放密码，只放『我是谁、何时过期』
- 第 3 段是防伪造的核心：服务器收到令牌后用密钥对前两段重算签名比对——改了内容签名就对不上
- **令牌 ≠ 密钥**：令牌是『盖了章的文件』（公开的），密钥是『印章』（只在服务器）。伪造者拿到一万张合法令牌也没用——改不了内容、造不出新令牌

## 1.5.4 两道门的区别：ACCESS_TOKEN vs JWT

| | 访问口令 ACCESS_TOKEN | 登录令牌 JWT |
|---|---|---|
| 是什么 | 固定暗号（.env 配置） | 服务器动态签发的电子凭证 |
| 谁有 | 所有用户共用同一个值 | 每用户每次登录一个独立值 |
| 校验方式 | 字符串相等比对 | 用密钥重算签名比对（防伪造） |
| 回答的问题 | 『你有没有进门资格』（网站级） | 『你是哪个用户』（用户级） |
| 有效期 | 前端存 7 天免输 | 72 小时 |
| 防什么 | 陌生人扫 IP 随便调接口 | 伪造身份冒充别人 |

**一次请求过两道门**：口令中间件先查『进门暗号』（不对直接 401，到不了业务逻辑）→ 需登录的接口再用 JWT 确认『你是用户 xxx』（查你自己的存档、你自己的图片）。口令挡扫描攻击，JWT 兜住登录后的数据隔离。

**中间件的豁免分支**：`/health` 健康检查（无敏感数据，监控工具免配置）和 `/draw/file/` 图片访问（img 标签带不了自定义头，该路由自带 HMAC 签名鉴权，安全不缺位）。

## 1.5.5 已知取舍

- JWT 存 localStorage：同设备其他网页脚本理论上可读（跨站脚本风险面）——个人项目可接受；更严格方案是 httpOnly Cookie（浏览器脚本读不到），实现复杂度上升
- 图片签名 URL 的重放风险与加固方案见《绘图工作台》4.5.4

- 口令校验：配置 ACCESS_TOKEN 后，/api 请求须带 X-Access-Token 头，不匹配返回 401；/api/health 放行；
- 输入防护：请求体限制 64KB，动作文本截断 200 字符；
- 出错回滚：AI 处理失败时把玩家输入从历史中回滚，避免污染上下文。

### 检查七：存储与权限

- 存档为 data/*.json，实例本地存储；
- .env 权限 664（组和其他用户可读）——风险项。

## 1.3 评估结论

1. **可以适配服务器部署**：后端有托管 frontend/dist 的代码，前端 API 用相对路径 /api（同源不跨域）；
2. **公网游玩可行**：防火墙 80 已放通，把服务跑在 80/443 即可；
3. **安全风险排序**：
   - 🔴 无 HTTPS：口令 X-Access-Token 明文传输，可被窃听；
   - 🔴 LLM 费用滥用：接口无速率限制，口令泄露后可无限调用消耗 API 费用；
   - 🟡 存档无用户隔离：知道口令的人共享存档空间，可互相删除；
   - 🟡 .env 权限过宽（664）；
   - 🟡 SSH 22 对全网开放；
   - 🟢 JSON 本地存储：可用性风险而非安全漏洞。

# 第二部分：概念讨论与方案确定（11:41 ～ 13:59）

这一阶段通过几轮问答澄清了关键概念，最终确定了部署方案。

## 2.1 HTTPS 怎么做？

约束条件：服务器在境内（上海）、只有公网 IP 没有域名、Express 单进程。

- **有域名路线**：买域名 → ICP 备案（境内服务器必须，数个工作日）→ 申请免费证书（腾讯云 SSL 或 Let's Encrypt）→ Nginx/Caddy 挂证书反代 → 防火墙放通 443；
- **无域名路线**：只能自签证书，加密有效但浏览器首次访问弹『不安全』警告，需手动点『继续访问』。

## 2.2 为什么选 Caddy？

Caddy 和 Nginx 一样是反向代理，区别在于 HTTPS 全自动：
- Nginx：自己申请、下载、配置、续期证书（免费证书 3 个月一过期）；
- Caddy：有域名时自动申请续期受信任证书；无域名时（配置里直接写 IP）自动生成自签证书，零操作。

配置对比：Nginx 实现『HTTPS + 反代 + 跳转』约 20～30 行；Caddy 只需：

```
124.220.208.156 {
    reverse_proxy localhost:3001
}
```

## 2.3 澄清：服务器上并没有在用 Nginx

评估已确认服务器无任何 Web 服务器软件。『用 Caddy 替代 Nginx』的真实含义是：将来部署时在『什么都不装』和『装一个门卫』之间，选后者且选 Caddy。

## 2.4 反向代理是什么？为什么不暴露 5173？

没有反代：手机要分别访问 5173（页面）和 3001（API），两个端口都暴露，内部结构全亮在外面。

有反代：

```
手机浏览器 → Caddy（80/443，唯一对外的门）
                └─ 所有请求 → 转发给 localhost:3001
```

好处：HTTPS 挂在门卫层（应用代码零改动）、端口收敛（只开 80/443）、同源（不触发跨域）、将来可扩展。

5173 是 Vite 开发服务器，定位是本机调试工具（不缓存、热更新、无加固），不该出现在生产环境。生产用构建好的静态文件。

## 2.5 .env 配置的含义

.env 是后端 Express 的配置文件，Vite 不读它。FRONTEND_ORIGIN 是后端的『访客来源白名单』（CORS）：填 5173 地址的含义是『允许从 5173 加载的页面调我的 API』——服务于开发模式。

用户当时已把它改为 http://124.220.208.156:5173（为『公网访问开发服务器』形态准备）。经讨论确认：采用 Caddy 生产形态后，页面和 API 同源，CORS 不触发，此配置不再起作用。

**最终处理（13:57）**：应用户要求改回原值并加注释：

```ini
# 前端来源（CORS 白名单）：仅在开发模式（Vite 5173 访问）下生效；
# 生产部署（Caddy 反代 / 后端直接托管 dist）为同源访问，不触发 CORS，此配置不生效
FRONTEND_ORIGIN=http://localhost:5173
```

## 2.6 一段重要的反复：『生产形态到底存不存在？』

用户质疑『你说我有生产形态的东西，我怎么不知道？我似乎从来没使用过，一直在用开发模式』。

排查过程（这个教训值得记录）：
1. 最初评估说『后端生产模式托管 frontend/dist』——结论正确；
2. 用户质疑后重新检索代码，检索工具两次返回『无匹配结果』（误报）；
3. 据误报推翻了正确结论，向用户『道歉更正』——造成了反复；
4. 用户要求重新阅读代码后，直接逐行读取原始代码，确认：

```js
// 生产模式：托管前端构建产物
const dist = path.join(__dirname, '..', 'frontend', 'dist');
app.use(express.static(dist));
```

**这段代码真实存在且无条件生效**。同时确认前端 src/api.js 中所有请求用相对路径：

```js
const res = await fetch(`/api${path}`, { ... })
```

**最终结论**：生产形态完整存在。用户『从来没用过』是因为一直用 dev.sh 启动、从 5173 入口访问——3001 的静态托管能力一直在那里，只是从未被这样访问过。

**教训**：结论必须建立在直接读取的原始代码上；工具返回异常时先复核工具，不要急着改口。

## 2.7 最终方案（13:59 用户授权执行）

1. Caddy 反代：对外仅 80/443，自签证书 HTTPS，反代本机 3001；

## 3.5 踩坑一：HTTPS 握手失败

**现象**：curl 访问 https 报错 `OpenSSL: error:0A000438:SSL routines::tlsv1 alert internal error`。

**排查**：
1. 查 Caddy 日志：证书签发其实成功了（certificate obtained successfully, issuer: local）；
2. curl -v 看握手详情：客户端发出 Client Hello 后，服务端直接回了 TLS alert。

**原因**：浏览器/curl 访问**纯 IP 地址**时，TLS 握手不携带 SNI（服务器名称指示）。Caddy 收到没有 SNI 的连接，不知道该用哪张证书，直接报内部错误。手机浏览器访问 IP 同样不带 SNI，所以必须修。

**解决**：Caddyfile 全局块加 `default_sni 124.220.208.156`——告诉 Caddy『没有 SNI 的连接默认用这张证书』。reload 后握手正常。

## 3.6 踩坑二：本机访问自己的公网 IP 卡住

**现象**：在服务器上 `curl https://124.220.208.156/...` 一直无响应（等待超时）。

**原因**：云服务器访问自身公网 IP 的回环链路不通，是云环境常见特性，不代表服务异常。

**解决**：验证时加 `--resolve 124.220.208.156:443:127.0.0.1`，把地址映射到本机回环——既走完整 TLS + 反代链路，又绕开网络特性。

## 3.7 放通防火墙 443

用户问『是不是我防火墙没给你开 443？』——正是如此。通过云接口添加规则：TCP 443，来源 0.0.0.0/0，ACCEPT，描述『HTTPS（Caddy 反代 AI 文字冒险游戏）』。

最终对外端口：22、80、443、ICMP；3001 不对公网暴露。

## 3.8 踩坑三：首页返回 401

**现象**：验证发现首页 HTTP 401——页面根本加载不出来。

**排查**：读后端代码，口令中间件写的是：

```js

```

它拦截**所有路径**，包括静态页面文件，而原意是只拦 /api。

**解决**：改为挂载在 /api 路径：

```js
app.use('/api', (req, res, next) => { ... })
```

页面正常加载，API 仍受口令保护（前端有 AccessGate 口令输入界面配合）。

**连带修复**：挂载到 /api 后 req.path 变成相对路径，健康检查放行判断从 `/api/health` 改为 `/health`，否则健康检查也会被误拦（验证时确实发现 /api/health 返回了 401）。

**排查**：读前端代码定位到时序问题——
1. App.vue 挂载时立即调用 game.refreshSaves()（请求存档列表）；

1. AccessGate.vue（前端门禁组件）：
   - 探测到 401 时立即清空 state.error（验证前的报错不该残留）；
   - 验证通过后调用 game.refreshSaves() 重新加载存档（既拿数据又清错误）；

## 4.4 问题：口令输入框不弹出，首页直接显示 + 错误提示残留

**用户反馈**：打开页面后没有弹出口令输入界面，而是直接显示了游戏首页（『文字冒险 / 选择模式 / 开始新冒险』等），下面还挂着一行『访问口令缺失或不正确，请输入正确的访问口令』和『尚无存档』提示。

**原因（这次是修改文案引入的连锁问题）**：

1. 前端口令门禁（AccessGate.vue）原来靠**文案关键词**识别『需要弹口令框』——判断错误信息里是否包含『未授权』或『401』字样；
2. 4.3 节优化后端 401 文案时，『未授权访问：…』被改成了『访问口令缺失或不正确…』——新文案两个关键词都不含；
3. 门禁识别失败：口令框没弹出、页面直接放行，401 错误信息残留在首页上。

**教训**：文案是给人看的，状态码才是给程序判断的。修改任何一端的『展示内容』前，必须检查另一端是否有对它的逻辑依赖。

**修复方式（根治而非改回文案）**：

1. **API 封装**（frontend/src/api.js）：请求失败抛错时在错误对象上附带 HTTP 状态码（err.status = res.status）；
2. **门禁组件**（AccessGate.vue）：判断逻辑从『文案包含关键词』改为『e.status === 401』。

这样无论后端文案将来怎么改，识别逻辑都不会再被破坏——展示与逻辑解耦。

# 第九部分：口令有效期改进（2026-10-11）

## 背景

用户提出：口令永久存在 localStorage 不够安全，希望 24 小时后需要重新输入。

## 分析过程

1. **localStorage 存口令的风险评估**：localStorage 可被同源页面任意 JS 读取，最大威胁是 XSS。检查确认前端未使用 v-html 渲染 LLM 生成的文本，Vue 默认转义文本——『AI 输出注入脚本偷口令』这条路走不通。残余风险仅为将来引入 v-html 或 npm 依赖投毒，概率低；
2. **方案对比**：
   - 方案 A：localStorage + 24 小时有效期（改动小，体验平滑）✅ 采纳；
   - 方案 B：sessionStorage（关浏览器即失效，便利性差）；
   - 方案 C：仅内存（刷新即失效，过度严格）；
   - 后端会话方案：安全性更强但改动大，对个人项目属过度设计。

## 实现（frontend/src/api.js）

- 存储结构从纯字符串改为 { token, savedAt }（口令 + 保存时间戳）；
- 读取时检查：超过 24 小时（TOKEN_TTL_MS）自动清除并返回空串 → 重新弹口令框；
- **旧格式兼容**：无时间戳的旧存储视为已过期，同样清除——升级后所有设备需重新验证一次。

## 验证

重新构建前端（1.86 秒），线上已切换为新版页面（index-BVtFAUPu.js），首页 200、API 无口令 401。

## 效果

- 24 小时内：同一设备免输入，体验不变；
- 超过 24 小时：自动清除，重新弹口令框；
- 清数据 / 无痕模式 / 换设备 / 修改 ACCESS_TOKEN：仍需重新输入（原有行为不变）。

# 第十一部分：口令验证后错误提示残留的根治（2026-10-11）

## 现象

用户反馈：输入正确口令进入游戏后，首页仍显示一行『访问口令缺失或不正确，请输入正确的访问口令』。

## 排查过程（基于代码事实，不凭推测）

1. 核实门禁组件当前代码：验证通过后的清理逻辑在位；
2. 追踪 state.error 的全部引用：首页（HomeView）在模板中渲染 state.error；
3. 关键发现——时序竞争：
   - 页面挂载时，App.vue 调用 refreshSaves()，HomeView 挂载时又调用 loadCatalogs() + refreshSaves()；
   - 这些请求在**口令验证完成之前**就已发出，返回 401 后把错误信息写入 state.error；
   - 门禁组件探测到 401 时虽然清了一次错误，但首页的请求**晚于清理动作**返回，错误又被写了回去；
   - 口令验证通过后，存档刷新成功但成功路径不清除旧错误——提示残留。

## 修复（两层，治本 + 兜底）

1. **源头治理（AccessGate.vue）**：增加探测中状态（probing）——验证完成前**不渲染游戏内容**，只显示『正在验证访问权限…』。首页组件根本不挂载，就不会发起过早的请求；验证通过后再渲染游戏内容并清除残留错误、重新加载存档；
2. **防御兜底（useGame.js）**：refreshSaves 和 loadCatalogs 的 catch 中，401 类错误不再写入 state.error——口令相关提示统一由门禁组件负责引导，即使将来出现新的时序竞争，口令类错误也不会残留在界面上。

## 验证

重新构建前端（1.68 秒），线上已切换为新版页面，首页 200、API 无口令 401。

## 教训

- **时序竞争是前端异步编程的隐蔽坑**：『清理了错误』不等于『错误不会再出现』——晚到的响应可以再次写入；
- **治本思路**：与其在错误出现后清理，不如让错误没有机会发生（验证前不渲染、不请求）；
- **职责分离**：口令引导是门禁的职责，数据加载函数不应把 401 当作页面错误展示。

# 第十二部分：游戏逻辑修复——身份冲突误判（2026-10-11）

## 现象

用户反馈：玩家名为 9 的存档（推理杀模式）中，第二天何欢的发言称『阿澈也声称自己是守卫』，但阿澈实际从未自称守卫。

## 核实过程（基于存档事实）

1. 定位存档文件 mv2fexnm-z975.json（推理杀模式）；
2. 读取身份声称记录（claims）：阿澈 → 文员；
3. 读取两轮发言：阿澈第一天自称『文员』并公布角色名册（帮凶、文员、守卫、狼人、村民、赌徒、侦探），第二天仍自称文员——**从未自称守卫**；
4. 何欢（真守卫）第二天发言：『而阿澈也声称自己是守卫——守卫只有一个，他在撒谎』——与事实矛盾，**用户反馈属实**。

## 根源（代码定位）

推理杀模式的『身份冲突检测』逻辑存在缺陷：

- 原判断：其他人的**发言文本中是否包含『守卫』二字** → 包含即判定为『有人冒称守卫』；
- 阿澈作为文员公布角色名册时**必然念到『守卫』这个词**——他只是在念名单，却被文字匹配误判为『自称守卫』；
- 程序随即向何欢注入错误情报：『阿澈自称是守卫，他必然是伪装者，你必须当众质疑他』；
- 何欢只是忠实转述了程序给的错误情报——**这不是 LLM 幻觉，而是程序逻辑 bug**。

## 修复

判断依据从『发言文本包含身份名』改为『结构化身份声称记录（claims）』：

```js
// 修复前：文字包含匹配（念名单会误判）
const rival = w.speeches.filter(...).find((s) => s.speech.includes(myRoleName));

// 修复后：结构化声称记录匹配（只看真正自称的身份）
const rival = (w.claims || []).find((c) => c.playerId !== p.id && c.claimed === myRoleName);
```

claims 是发言后程序从『我是X』提取的结构化数据，不受念名单影响。

## 验证

- 语法检查通过（node --check）；
- 后端重启成功，进程 online，健康检查 {"ok":true,"llm":true}。

## 说明与教训

- **已产生的存档不会自动修正**：历史发言已落盘，修复只保证后续对局不再出现此类误判；
- **教训一**：判断『某人说了什么』要用结构化数据，不要用文本包含匹配——自然语言中一个词的出现有无数种语境（念名单、转述、质疑都包含该词）；
- **教训二**：排查『AI 说了错话』类问题，先区分是模型幻觉还是程序注入的错误情报——本例中 AI 忠实执行了错误指令，病根在代码。

# 第十三部分：推理杀发言质量修复与实测（2026-10-11）

## 测试发现的问题（2 局完整试玩）

以法官身份通过 API 完整对局 2 局，发现：
1. **严重**：存活者被说成已死（孟瑶、周舟都说存活的阿澈『被袭击身亡』，实际死的是老陈）；
2. **严重**：AI 自言自语（周舟发言结尾问『周舟，你的判断？』）；
3. **中等**：人称错乱（孟瑶说『老陈查验了我和孟瑶』——把自己当外人；林晚同一句里『我』和『林晚』混用）；
4. **中等**：信息遗漏（三人自称侦探，文员只指出两人冲突）；
5. **轻微**：处刑已死玩家无明确报错。

## 根源

发言提示词中只注入了存活名单，**没有死亡名单**，也没有人称与生死的纪律约束——模型在长上下文中混淆生死状态、用名字称呼自己。信息遗漏则是冲突检测用 find 只返回第一个匹配者。

## 修复（三处）

1. **注入死亡名单硬信息**：提示词中新增结构化的死者列表（姓名 + 第几天 + 死因），与存活名单并列；
2. **新增两条铁律**：『生死状态铁律』（绝不能说存活者已死、不能把死者当在场者讨论）和『人称纪律铁律』（始终用第一人称『我』，绝不用自己名字称呼自己）；
3. **冲突检测升级**：从 find（只找一个对手）改为 filter（找出全部自称者），三人同称侦探时 AI 能知道全部对手。

## 实测验证（第 3 局完整对局）

- ✅ 无存活者被说成已死；
- ✅ 无自言自语、人称正常；
- ✅ 多人身份冲突检测生效：何欢与许诺双法医对跳时，许诺正确指出『何欢也自称法医，同一身份不可能两人』；孟瑶正确推理『周舟是守卫，与老陈自称守卫冲突』；
- ⚠️ 轻微残留：法医第 2 天说『昨夜已验明周舟尸体』——周舟死于第 1 夜，时间指代略有偏差，属模型表达瑕疵，不影响游戏逻辑，暂不处理。

## 方法论沉淀

『AI 说错话』的三层排查框架：① 程序注入的情报是否正确（第十二部分案例）；② 模型上下文中是否有足够的结构化硬信息（本部分案例）；③ 提示词纪律约束是否覆盖已知错误模式。修复优先给模型喂对信息（1、2），其次才是加纪律约束（3）——信息对了，纪律才有力。

# 附录三：命令学习手册（部署全程关键命令逐条解读）

本附录把部署过程中真实执行过的关键命令集中起来，按『命令 → 真实输出 → 怎么解读』的格式讲解。初学者可以逐条对照学习：每条命令为什么用、输出里的每个字段是什么意思。

## A. 排查类命令（先看清楚现状再动手）

### A1. 查看目录结构

```bash
ls -la /home/ubuntu/Whatever
```

真实输出（节选）：

```
drwxrwxr-x 7 ubuntu ubuntu  4096 Oct 10 10:11 .
drwxr-x--- 6 ubuntu ubuntu  4096 Oct 10 10:11 ..
drwxrwxr-x 2 ubuntu ubuntu  4096 Oct 10 10:11 data
-rw-rw-r-- 1 ubuntu ubuntu  322 Oct 10 11:31 .env
-rwxrwxr-x 1 ubuntu ubuntu  575 Oct 10 10:12 dev.sh
```

**解读**：
- 第一列是权限：`d` 开头是目录，`-` 开头是文件；`rwx` 分别是读/写/执行，三组依次属于『所有者/组/其他人』。`.env` 是 `-rw-rw-r--`（664），意味着其他用户也能读——这就是后来要 `chmod 600` 的原因；
- 第三、四列是属主和属组；
- 倒数第二列是大小（字节），最后一列是修改时间——**对比文件时间戳是排查『改了没生效』类问题的关键手段**（见 4.2 节口令失灵的定位）。

### A2. 查看进程和端口监听

```bash
ps aux | grep -E 'node|vite' | grep -v grep
ss -tlnp
```

真实输出（节选）：

```
LISTEN 0  4096  0.0.0.0:22   0.0.0.0:*  users:(("sshd",pid=1024,fd=3))
LISTEN 0  511   *:3001       *:*        users:(("node /home/ubuntu/ubun",pid=72051,fd=22))
```

**解读**：

**解读**：排查配置问题时，尽量只提取需要的信息，避免把密钥整个打印到终端/日志里。`awk -F=` 按 `=` 分割，`$2` 是等号后的值，`length()` 取长度——这样能确认『口令是 43 位、没被截断』而不暴露口令本身。

### C1. curl 验证 HTTP 接口

```bash

```

真实输出：

```

```

**逐个参数解读**：

### C2. 本机回环验证技巧（云服务器特有）

```bash

```

**解读**：`--resolve 地址:端口:实际IP` 相当于临时改了一条 DNS——请求名义上访问公网 IP（TLS 握手用对的名字），实际连到 127.0.0.1（本机）。为什么需要它：云服务器访问自己的公网 IP 常常不通（回环路由问题），直接 curl 会卡死；用这个技巧既完整验证了『TLS 握手 + Caddy 反代 + 后端响应』全链路，又绕开了网络特性。**注意**：这只验证服务本身正常，公网可达性还需防火墙放通 + 外部设备实测。

### C3. 验证口令认证链路


真实输出：

```

```

**解读**：
- `TOKEN=$(命令)` 把命令输出存进变量（命令替换），避免口令出现在命令行历史里；

这一阶段通过几轮问答澄清了关键概念，最终确定了部署方案。

## 2.1 HTTPS 怎么做？

约束条件：服务器在境内（上海）、只有公网 IP 没有域名、Express 单进程。

- **有域名路线**：买域名 → ICP 备案（境内服务器必须，数个工作日）→ 申请免费证书（腾讯云 SSL 或 Let's Encrypt）→ Nginx/Caddy 挂证书反代 → 防火墙放通 443；
- **无域名路线**：只能自签证书，加密有效但浏览器首次访问弹『不安全』警告，需手动点『继续访问』。

## 2.2 为什么选 Caddy？

Caddy 和 Nginx 一样是反向代理，区别在于 HTTPS 全自动：
- Nginx：自己申请、下载、配置、续期证书（免费证书 3 个月一过期）；
- Caddy：有域名时自动申请续期受信任证书；无域名时（配置里直接写 IP）自动生成自签证书，零操作。

配置对比：Nginx 实现『HTTPS + 反代 + 跳转』约 20～30 行；Caddy 只需：

```
124.220.208.156 {
    reverse_proxy localhost:3001
}
```

## 2.3 澄清：服务器上并没有在用 Nginx

评估已确认服务器无任何 Web 服务器软件。『用 Caddy 替代 Nginx』的真实含义是：将来部署时在『什么都不装』和『装一个门卫』之间，选后者且选 Caddy。

## 2.4 反向代理是什么？为什么不暴露 5173？

没有反代：手机要分别访问 5173（页面）和 3001（API），两个端口都暴露，内部结构全亮在外面。

有反代：

```
手机浏览器 → Caddy（80/443，唯一对外的门）
                └─ 所有请求 → 转发给 localhost:3001
```

好处：HTTPS 挂在门卫层（应用代码零改动）、端口收敛（只开 80/443）、同源（不触发跨域）、将来可扩展。

5173 是 Vite 开发服务器，定位是本机调试工具（不缓存、热更新、无加固），不该出现在生产环境。生产用构建好的静态文件。

## 2.5 .env 配置的含义

.env 是后端 Express 的配置文件，Vite 不读它。FRONTEND_ORIGIN 是后端的『访客来源白名单』（CORS）：填 5173 地址的含义是『允许从 5173 加载的页面调我的 API』——服务于开发模式。

用户当时已把它改为 http://124.220.208.156:5173（为『公网访问开发服务器』形态准备）。经讨论确认：采用 Caddy 生产形态后，页面和 API 同源，CORS 不触发，此配置不再起作用。

**最终处理（13:57）**：应用户要求改回原值并加注释：

```ini
# 前端来源（CORS 白名单）：仅在开发模式（Vite 5173 访问）下生效；
# 生产部署（Caddy 反代 / 后端直接托管 dist）为同源访问，不触发 CORS，此配置不生效
FRONTEND_ORIGIN=http://localhost:5173
```

## 2.6 一段重要的反复：『生产形态到底存不存在？』

用户质疑『你说我有生产形态的东西，我怎么不知道？我似乎从来没使用过，一直在用开发模式』。

排查过程（这个教训值得记录）：
1. 最初评估说『后端生产模式托管 frontend/dist』——结论正确；
2. 用户质疑后重新检索代码，检索工具两次返回『无匹配结果』（误报）；
3. 据误报推翻了正确结论，向用户『道歉更正』——造成了反复；
4. 用户要求重新阅读代码后，直接逐行读取原始代码，确认：

```js
// 生产模式：托管前端构建产物
const dist = path.join(__dirname, '..', 'frontend', 'dist');
app.use(express.static(dist));
```

**这段代码真实存在且无条件生效**。同时确认前端 src/api.js 中所有请求用相对路径：

```js
const res = await fetch(`/api${path}`, { ... })
```

**最终结论**：生产形态完整存在。用户『从来没用过』是因为一直用 dev.sh 启动、从 5173 入口访问——3001 的静态托管能力一直在那里，只是从未被这样访问过。

**教训**：结论必须建立在直接读取的原始代码上；工具返回异常时先复核工具，不要急着改口。

## 2.7 最终方案（13:59 用户授权执行）

## 3.3 编写 Caddy 配置

先创建目录（二进制安装不会自带）：`mkdir -p /etc/caddy /var/lib/caddy`

（第一次写配置失败，报错 No such file or directory，就是因为目录不存在。）

最终配置 /etc/caddy/Caddyfile：

```
# 纯 IP 访问时客户端不发送 SNI，需指定默认 SNI 才能匹配到证书
{
	default_sni 124.220.208.156
}

124.220.208.156 {
	# 所有请求（页面 + /api）统一反代到本机后端
	reverse_proxy localhost:3001
}
```

（default_sni 是后来踩坑后补的，见 3.5。）

## 3.4 创建 systemd 服务

二进制安装没有服务文件，手写 /etc/systemd/system/caddy.service：

```ini
[Unit]
Description=Caddy
After=network.target network-online.target

[Service]
Type=notify
User=root
ExecStart=/usr/local/bin/caddy run --environ --config /etc/caddy/Caddyfile
ExecReload=/usr/local/bin/caddy reload --config /etc/caddy/Caddyfile --force
TimeoutStopSec=5s
LimitNOFILE=1048576

[Install]
WantedBy=multi-user.target
```

启动：`systemctl daemon-reload && systemctl enable --now caddy`

验证：配置语法 Valid、服务 active、监听 80 和 443。

## 3.5 踩坑一：HTTPS 握手失败

**现象**：curl 访问 https 报错 `OpenSSL: error:0A000438:SSL routines::tlsv1 alert internal error`。

**排查**：
1. 查 Caddy 日志：证书签发其实成功了（certificate obtained successfully, issuer: local）；
2. curl -v 看握手详情：客户端发出 Client Hello 后，服务端直接回了 TLS alert。

**原因**：浏览器/curl 访问**纯 IP 地址**时，TLS 握手不携带 SNI（服务器名称指示）。Caddy 收到没有 SNI 的连接，不知道该用哪张证书，直接报内部错误。手机浏览器访问 IP 同样不带 SNI，所以必须修。

**解决**：Caddyfile 全局块加 `default_sni 124.220.208.156`——告诉 Caddy『没有 SNI 的连接默认用这张证书』。reload 后握手正常。

## 3.6 踩坑二：本机访问自己的公网 IP 卡住

**现象**：在服务器上 `curl https://124.220.208.156/...` 一直无响应（等待超时）。

**原因**：云服务器访问自身公网 IP 的回环链路不通，是云环境常见特性，不代表服务异常。

**解决**：验证时加 `--resolve 124.220.208.156:443:127.0.0.1`，把地址映射到本机回环——既走完整 TLS + 反代链路，又绕开网络特性。

## 3.7 放通防火墙 443

用户问『是不是我防火墙没给你开 443？』——正是如此。通过云接口添加规则：TCP 443，来源 0.0.0.0/0，ACCEPT，描述『HTTPS（Caddy 反代 AI 文字冒险游戏）』。

最终对外端口：22、80、443、ICMP；3001 不对公网暴露。

## 3.8 踩坑三：首页返回 401

**现象**：验证发现首页 HTTP 401——页面根本加载不出来。

**排查**：读后端代码，口令中间件写的是：

```js
app.use((req, res, next) => { ... })
```

它拦截**所有路径**，包括静态页面文件，而原意是只拦 /api。

**解决**：改为挂载在 /api 路径：

```js
app.use('/api', (req, res, next) => { ... })
```

页面正常加载，API 仍受口令保护（前端有 AccessGate 口令输入界面配合）。

**连带修复**：挂载到 /api 后 req.path 变成相对路径，健康检查放行判断从 `/api/health` 改为 `/health`，否则健康检查也会被误拦（验证时确实发现 /api/health 返回了 401）。

## 4.1 用户问：输入访问口令会泄密吗？

结论：**正常使用不会泄密**。
- 安全环节：传输全程 TLS 加密；口令只存服务端 .env（600 权限）；前端代码里没有口令；服务端只比对不记录；

5. 对比时间戳发现真正问题：

## 4.3 问题：进入游戏后残留错误提示

**用户反馈**：输入正确口令进入游戏后，界面仍有一行『未授权访问：请输入正确的访问口令（首次进入页面时提示）』。

**排查**：读前端代码定位到时序问题——
1. App.vue 挂载时立即调用 game.refreshSaves()（请求存档列表）；
2. 此时口令尚未验证，请求返回 401，错误信息写入 state.error 显示在页面上；
3. 口令验证通过后，没人清除这行错误——一直残留。

**修复（两处）**：

1. AccessGate.vue（前端门禁组件）：
   - 探测到 401 时立即清空 state.error（验证前的报错不该残留）；
   - 验证通过后调用 game.refreshSaves() 重新加载存档（既拿数据又清错误）；
2. 后端 401 文案：『未授权访问：请输入正确的访问口令（首次进入页面时提示）』→『访问口令缺失或不正确，请输入正确的访问口令』（去掉对玩家无意义的括号说明）。

重新构建前端 + 重启后端后验证：首页 200、API 无口令 401（新文案）、进程 online。

## 4.4 问题：口令输入框不弹出，首页直接显示 + 错误提示残留

**用户反馈**：打开页面后没有弹出口令输入界面，而是直接显示了游戏首页（『文字冒险 / 选择模式 / 开始新冒险』等），下面还挂着一行『访问口令缺失或不正确，请输入正确的访问口令』和『尚无存档』提示。

**原因（这次是修改文案引入的连锁问题）**：

1. 前端口令门禁（AccessGate.vue）原来靠**文案关键词**识别『需要弹口令框』——判断错误信息里是否包含『未授权』或『401』字样；
2. 4.3 节优化后端 401 文案时，『未授权访问：…』被改成了『访问口令缺失或不正确…』——新文案两个关键词都不含；
3. 门禁识别失败：口令框没弹出、页面直接放行，401 错误信息残留在首页上。

**教训**：文案是给人看的，状态码才是给程序判断的。修改任何一端的『展示内容』前，必须检查另一端是否有对它的逻辑依赖。

**修复方式（根治而非改回文案）**：

1. **API 封装**（frontend/src/api.js）：请求失败抛错时在错误对象上附带 HTTP 状态码（err.status = res.status）；
2. **门禁组件**（AccessGate.vue）：判断逻辑从『文案包含关键词』改为『e.status === 401』。

这样无论后端文案将来怎么改，识别逻辑都不会再被破坏——展示与逻辑解耦。

**验证**：重新构建前端（1.63 秒）后，线上页面已更新，首页 200、API 无口令 401。打开页面直接弹出口令输入界面，输入正确口令后干净进入游戏。

**关于 HTTPS 的确认**：本轮所有修复均为前端页面代码更新，不涉及访问链路变化——全程仍走 https://124.220.208.156（443 端口，Caddy 自签证书 TLS 加密），HTTP 访问仍自动 308 跳转 HTTPS。

# 第九部分：口令有效期改进（2026-10-11）

## 背景

用户提出：口令永久存在 localStorage 不够安全，希望 24 小时后需要重新输入。

## 分析过程

1. **localStorage 存口令的风险评估**：localStorage 可被同源页面任意 JS 读取，最大威胁是 XSS。检查确认前端未使用 v-html 渲染 LLM 生成的文本，Vue 默认转义文本——『AI 输出注入脚本偷口令』这条路走不通。残余风险仅为将来引入 v-html 或 npm 依赖投毒，概率低；
2. **方案对比**：
   - 方案 A：localStorage + 24 小时有效期（改动小，体验平滑）✅ 采纳；
   - 方案 B：sessionStorage（关浏览器即失效，便利性差）；
   - 方案 C：仅内存（刷新即失效，过度严格）；
   - 后端会话方案：安全性更强但改动大，对个人项目属过度设计。

## 实现（frontend/src/api.js）

- 存储结构从纯字符串改为 { token, savedAt }（口令 + 保存时间戳）；
- 读取时检查：超过 24 小时（TOKEN_TTL_MS）自动清除并返回空串 → 重新弹口令框；
- **旧格式兼容**：无时间戳的旧存储视为已过期，同样清除——升级后所有设备需重新验证一次。

## 验证

重新构建前端（1.86 秒），线上已切换为新版页面（index-BVtFAUPu.js），首页 200、API 无口令 401。

## 效果

- 24 小时内：同一设备免输入，体验不变；
- 超过 24 小时：自动清除，重新弹口令框；
- 清数据 / 无痕模式 / 换设备 / 修改 ACCESS_TOKEN：仍需重新输入（原有行为不变）。

# 第十一部分：口令验证后错误提示残留的根治（2026-10-11）

## 现象

用户反馈：输入正确口令进入游戏后，首页仍显示一行『访问口令缺失或不正确，请输入正确的访问口令』。

## 排查过程（基于代码事实，不凭推测）

1. 核实门禁组件当前代码：验证通过后的清理逻辑在位；
2. 追踪 state.error 的全部引用：首页（HomeView）在模板中渲染 state.error；
3. 关键发现——时序竞争：
   - 页面挂载时，App.vue 调用 refreshSaves()，HomeView 挂载时又调用 loadCatalogs() + refreshSaves()；
   - 这些请求在**口令验证完成之前**就已发出，返回 401 后把错误信息写入 state.error；
   - 门禁组件探测到 401 时虽然清了一次错误，但首页的请求**晚于清理动作**返回，错误又被写了回去；
   - 口令验证通过后，存档刷新成功但成功路径不清除旧错误——提示残留。

## 修复（两层，治本 + 兜底）

1. **源头治理（AccessGate.vue）**：增加探测中状态（probing）——验证完成前**不渲染游戏内容**，只显示『正在验证访问权限…』。首页组件根本不挂载，就不会发起过早的请求；验证通过后再渲染游戏内容并清除残留错误、重新加载存档；
2. **防御兜底（useGame.js）**：refreshSaves 和 loadCatalogs 的 catch 中，401 类错误不再写入 state.error——口令相关提示统一由门禁组件负责引导，即使将来出现新的时序竞争，口令类错误也不会残留在界面上。

## 验证

重新构建前端（1.68 秒），线上已切换为新版页面，首页 200、API 无口令 401。

## 教训

- **时序竞争是前端异步编程的隐蔽坑**：『清理了错误』不等于『错误不会再出现』——晚到的响应可以再次写入；
- **治本思路**：与其在错误出现后清理，不如让错误没有机会发生（验证前不渲染、不请求）；
- **职责分离**：口令引导是门禁的职责，数据加载函数不应把 401 当作页面错误展示。

# 第十二部分：游戏逻辑修复——身份冲突误判（2026-10-11）

## 现象

用户反馈：玩家名为 9 的存档（推理杀模式）中，第二天何欢的发言称『阿澈也声称自己是守卫』，但阿澈实际从未自称守卫。

## 核实过程（基于存档事实）

1. 定位存档文件 mv2fexnm-z975.json（推理杀模式）；
2. 读取身份声称记录（claims）：阿澈 → 文员；
3. 读取两轮发言：阿澈第一天自称『文员』并公布角色名册（帮凶、文员、守卫、狼人、村民、赌徒、侦探），第二天仍自称文员——**从未自称守卫**；
4. 何欢（真守卫）第二天发言：『而阿澈也声称自己是守卫——守卫只有一个，他在撒谎』——与事实矛盾，**用户反馈属实**。

## 根源（代码定位）

推理杀模式的『身份冲突检测』逻辑存在缺陷：

- 原判断：其他人的**发言文本中是否包含『守卫』二字** → 包含即判定为『有人冒称守卫』；
- 阿澈作为文员公布角色名册时**必然念到『守卫』这个词**——他只是在念名单，却被文字匹配误判为『自称守卫』；
- 程序随即向何欢注入错误情报：『阿澈自称是守卫，他必然是伪装者，你必须当众质疑他』；
- 何欢只是忠实转述了程序给的错误情报——**这不是 LLM 幻觉，而是程序逻辑 bug**。

## 修复

判断依据从『发言文本包含身份名』改为『结构化身份声称记录（claims）』：

```js
// 修复前：文字包含匹配（念名单会误判）
const rival = w.speeches.filter(...).find((s) => s.speech.includes(myRoleName));

// 修复后：结构化声称记录匹配（只看真正自称的身份）
const rival = (w.claims || []).find((c) => c.playerId !== p.id && c.claimed === myRoleName);
```

claims 是发言后程序从『我是X』提取的结构化数据，不受念名单影响。

## 验证

- 语法检查通过（node --check）；
- 后端重启成功，进程 online，健康检查 {"ok":true,"llm":true}。

## 说明与教训

- **已产生的存档不会自动修正**：历史发言已落盘，修复只保证后续对局不再出现此类误判；
- **教训一**：判断『某人说了什么』要用结构化数据，不要用文本包含匹配——自然语言中一个词的出现有无数种语境（念名单、转述、质疑都包含该词）；
- **教训二**：排查『AI 说了错话』类问题，先区分是模型幻觉还是程序注入的错误情报——本例中 AI 忠实执行了错误指令，病根在代码。

# 第十三部分：推理杀发言质量修复与实测（2026-10-11）

## 测试发现的问题（2 局完整试玩）

以法官身份通过 API 完整对局 2 局，发现：
1. **严重**：存活者被说成已死（孟瑶、周舟都说存活的阿澈『被袭击身亡』，实际死的是老陈）；
2. **严重**：AI 自言自语（周舟发言结尾问『周舟，你的判断？』）；
3. **中等**：人称错乱（孟瑶说『老陈查验了我和孟瑶』——把自己当外人；林晚同一句里『我』和『林晚』混用）；
4. **中等**：信息遗漏（三人自称侦探，文员只指出两人冲突）；
5. **轻微**：处刑已死玩家无明确报错。

## 根源

发言提示词中只注入了存活名单，**没有死亡名单**，也没有人称与生死的纪律约束——模型在长上下文中混淆生死状态、用名字称呼自己。信息遗漏则是冲突检测用 find 只返回第一个匹配者。

## 修复（三处）

1. **注入死亡名单硬信息**：提示词中新增结构化的死者列表（姓名 + 第几天 + 死因），与存活名单并列；
2. **新增两条铁律**：『生死状态铁律』（绝不能说存活者已死、不能把死者当在场者讨论）和『人称纪律铁律』（始终用第一人称『我』，绝不用自己名字称呼自己）；
3. **冲突检测升级**：从 find（只找一个对手）改为 filter（找出全部自称者），三人同称侦探时 AI 能知道全部对手。

## 实测验证（第 3 局完整对局）

- ✅ 无存活者被说成已死；
- ✅ 无自言自语、人称正常；
- ✅ 多人身份冲突检测生效：何欢与许诺双法医对跳时，许诺正确指出『何欢也自称法医，同一身份不可能两人』；孟瑶正确推理『周舟是守卫，与老陈自称守卫冲突』；
- ⚠️ 轻微残留：法医第 2 天说『昨夜已验明周舟尸体』——周舟死于第 1 夜，时间指代略有偏差，属模型表达瑕疵，不影响游戏逻辑，暂不处理。

## 方法论沉淀

『AI 说错话』的三层排查框架：① 程序注入的情报是否正确（第十二部分案例）；② 模型上下文中是否有足够的结构化硬信息（本部分案例）；③ 提示词纪律约束是否覆盖已知错误模式。修复优先给模型喂对信息（1、2），其次才是加纪律约束（3）——信息对了，纪律才有力。

# 附录三：命令学习手册（部署全程关键命令逐条解读）

本附录把部署过程中真实执行过的关键命令集中起来，按『命令 → 真实输出 → 怎么解读』的格式讲解。初学者可以逐条对照学习：每条命令为什么用、输出里的每个字段是什么意思。

## A. 排查类命令（先看清楚现状再动手）

### A1. 查看目录结构

```bash
ls -la /home/ubuntu/Whatever
```

真实输出（节选）：

```
drwxrwxr-x 7 ubuntu ubuntu  4096 Oct 10 10:11 .
drwxr-x--- 6 ubuntu ubuntu  4096 Oct 10 10:11 ..
drwxrwxr-x 2 ubuntu ubuntu  4096 Oct 10 10:11 data
-rw-rw-r-- 1 ubuntu ubuntu  322 Oct 10 11:31 .env
-rwxrwxr-x 1 ubuntu ubuntu  575 Oct 10 10:12 dev.sh
```

**解读**：
- 第一列是权限：`d` 开头是目录，`-` 开头是文件；`rwx` 分别是读/写/执行，三组依次属于『所有者/组/其他人』。`.env` 是 `-rw-rw-r--`（664），意味着其他用户也能读——这就是后来要 `chmod 600` 的原因；
- 第三、四列是属主和属组；
- 倒数第二列是大小（字节），最后一列是修改时间——**对比文件时间戳是排查『改了没生效』类问题的关键手段**（见 4.2 节口令失灵的定位）。

### A2. 查看进程和端口监听

```bash
ps aux | grep -E 'node|vite' | grep -v grep
ss -tlnp
```

真实输出（节选）：

```
LISTEN 0  4096  0.0.0.0:22   0.0.0.0:*  users:(("sshd",pid=1024,fd=3))
LISTEN 0  511   *:3001       *:*        users:(("node /home/ubuntu/ubun",pid=72051,fd=22))
```

**解读**：
- `ps aux` 列出所有进程，`grep -E 'node|vite'` 过滤出含关键词的行，`grep -v grep` 再排除 grep 自己；
- `ss -tlnp`：`t`=TCP、`l`=只看监听、`n`=显示数字端口、`p`=显示占用进程。每行一个监听端口：`0.0.0.0:22` 表示监听所有网卡的 22 端口（对外可达），`*:3001` 同理；如果显示 `127.0.0.1:3001` 则表示只监听本机回环（外部访问不到）；
- **用途**：判断『服务到底起没起、监听在哪个地址』。评估阶段用它确认了项目未运行；部署后用它确认后端监听 3001、Caddy 监听 80/443。

### A3. 查看配置项（不泄露密钥的技巧）

```bash
sed 's/=.*/=<已隐藏>/' .env          # 只看键名，值全部替换
grep -E '^(FRONTEND_ORIGIN|PORT)=' .env  # 只提取指定的非敏感项
awk -F= '/^ACCESS_TOKEN=/{v=$2; print "口令长度: " length(v)}' .env  # 只看长度不看内容
```

**解读**：排查配置问题时，尽量只提取需要的信息，避免把密钥整个打印到终端/日志里。`awk -F=` 按 `=` 分割，`$2` 是等号后的值，`length()` 取长度——这样能确认『口令是 43 位、没被截断』而不暴露口令本身。

### A4. 确认文件真实类型（下载类问题的第一步）

```bash
file /tmp/caddy.tar.gz
```

真实输出：

```
caddy.tar.gz: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked
```

## 14.6 验证账号体系（正反两面测试）

**正面：注册并登录**

```bash
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"测试玩家A","password":"test123456"}' \
  http://localhost:3001/api/auth/register
```

**解读**：
- `-X POST`：指定 HTTP 方法为 POST（创建数据用 POST，查询用 GET，删除用 DELETE——这是 RESTful 接口的通用约定）；
- `-H 'Content-Type: application/json'`：告诉服务器『我发的 body 是 JSON 格式』，不写这行服务器会解析失败；
- `-d '...'`：请求体。注意外层用单引号包裹，内部 JSON 的字符串用双引号——引号嵌套是命令行最常见的坑；
- 末尾 `\` 是续行符，让一条长命令分多行写，提高可读性；
- 成功返回 `{"token":"eyJ...","user":{...}}`——token 就是登录凭证，后续每个请求带上它，服务器就知道『你是谁』。

**反面：验证隔离（核心安全测试）**

```bash
# 用玩家B的 token 访问玩家A的存档
curl -s -w 'HTTP %{http_code}' -H "Authorization: Bearer $TB" \
  http://localhost:3001/api/games/$GID
# 期望输出：{"error":"存档不存在"}HTTP 404
```

**解读**：
- `-w 'HTTP %{http_code}'`：让 curl 在输出末尾追加 HTTP 状态码——200=成功、401=未登录、404=不存在。**看状态码比看返回内容更可靠**；
- `-H "Authorization: Bearer $TB"`：携带玩家 B 的登录凭证。Bearer 是 JWT 的标准携带格式（『持有此令牌者』）；
- **为什么期望 404 而不是 403**：403（禁止）会告诉攻击者『这个存档存在但你没权限』，等于泄露了信息；404（不存在）让攻击者无法区分『不存在』和『无权访问』——这是安全设计里的『不暴露存在性』原则。

# 第十五部分：从改代码到上线——部署与运行原理完整讲解（2026-10-19）

> 本部分沉淀自一次完整的问答式学习：从『对部署一无所知』出发，讲清改代码之后到线上生效的全过程。所有代码与文件均引用自本项目真实状态，可对照源码阅读。

## 15.1 全流程总览：改了代码之后发生了什么

项目分两部分，上线方式完全不同：
- 前端（frontend/）：Vue 组件，浏览器不认识，必须先『编译』成纯静态文件才能上线
- 后端（server/）：Node.js 脚本，不需要编译，Node 直接运行

完整流程：

```
本地改代码 → git push ──────────────→ GitHub
                                        │
服务器：git pull → (装依赖) → 构建前端 → pm2 restart → 验证
```

具体步骤与命令：

```bash
# 1. 本地开发验证（热更新，改完即见效果）
npm run play

# 2. 提交代码（此时线上没有任何变化）
git add -A
git commit -m '描述这次改了什么'
git push origin main

# 3. 登录服务器拉取最新代码
ssh root@服务器IP
cd /home/ubuntu/Whatever
git pull origin main

# 4. 装依赖（仅当 package.json 有变化时）
npm run install:all

# 5. 构建前端（改了 frontend/ 就必须做）
npm run build:frontend
# Vite 把所有 .vue 组件编译打包，输出到 frontend/dist/
# dist 被 .gitignore 忽略，必须在服务器上现场构建

# 6. 重启服务进程

# 7. 验证
pm2 status ai-rpg                          # 确认 online
curl -s http://localhost:3001/api/health   # 确认接口正常
```

日常迭代最常敲的就是四条：git pull → npm run build:frontend → pm2 restart ai-rpg → 验证。

## 15.2 pm2 与 ai-rpg：进程管理的本质

ai-rpg 不是代码，是进程的『名字』（别名），不在项目文件里。它来自最初部署时的命令：

```bash
pm2 start server/index.js --name ai-rpg
```

pm2 内部维护一张进程表，记住了：名字叫 ai-rpg、入口脚本是 server/index.js、工作目录是项目根。之后就能用这个名字指挥它：

```bash
pm2 restart ai-rpg   # 重启
pm2 status ai-rpg    # 看状态
pm2 logs ai-rpg      # 看日志
```

pm2 不是运行环境，只是个保姆：任何 node 脚本它都能启动，本质是替你执行 node server/index.js，并额外提供三件事：崩溃自动重启、服务器重启后自动拉起（配合 pm2 save 存盘）、日志收集。没有 pm2 手动敲 node server/index.js 也能跑，只是关掉终端进程就死了。

为什么改代码要重启：Node 进程启动时把代码读进内存，之后磁盘文件再怎么改，运行中的进程用的还是内存里的旧代码。重启 = 让进程重新读一遍最新文件。

## 15.3 单进程前后端一体架构

前端没有任何进程在『运行』——dist 里的文件只是躺在磁盘上。Express 进程（ai-rpg）用 express.static 顺带把静态文件托管了，所以一个进程、一个端口跑整个应用：

```
用户浏览器 ──→ Caddy 反代 ──→ ai-rpg 进程（127.0.0.1:3001）
                              ├─ /api/xxx  → 跑后端逻辑
                              └─ 其他请求  → 返回 dist 里的静态文件
```

生产环境 HOST=127.0.0.1 只监听本机，外部流量一律经 Caddy 反向代理进入（纵深防御，公网无法直连后端端口）。

改了后端（server/）→ 必须重启；只改前端 → 静态文件其实即时生效，但重启一下最稳妥。

## 15.5 SQLite：建表是什么，旧库迁移干什么

SQLite 数据库就是一个文件（data/game.db）。表（table）相当于 Excel 里的一张工作表：列（字段）= 表头，行 = 一条记录。建表 = 画出表头结构，必须先有结构才能填数据。

```sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,           -- 用户唯一编号
  username TEXT UNIQUE NOT NULL, -- 用户名，不许重复
  password_hash TEXT NOT NULL,   -- 密码（scrypt 哈希，不存明文）
  created_at INTEGER NOT NULL,   -- 注册时间
  is_admin INTEGER DEFAULT 0     -- 是否管理员，默认不是
);
```

IF NOT EXISTS 的意义：这段代码每次启动都执行。第一次启动建表；之后发现表已存在就跳过，不会清空数据。库里有 5 张表：users / saves / draw_history / draw_prompts / online_sessions。

旧库迁移：项目是先上线后加功能的。老库已存在，CREATE TABLE IF NOT EXISTS 一看表在直接跳过——新加的列永远不会出现在老库里，代码一查就报错。迁移就是给老库『补装修』：

```js
try { db.exec('ALTER TABLE users ADD COLUMN is_admin INTEGER DEFAULT 0'); } catch { /* 字段已存在 */ }
```

- 老库：加列成功，原有数据原封不动，所有老账号一次性集体获得新字段（默认值 0）
- 新库：建表时已有此列，再加报错 → catch 接住忽略

一份代码同时兼容新老两种库。老库只在第一次启动时被真正修改一次，之后结构与新库完全一致，不再有新老之分。迁移代码一般留着不删：防呆（老备份恢复时还能救一次）且无害（每次启动多三条注定失败的 SQL，开销可忽略）。

## 15.6 管理员名单为什么要从 .env 同步到数据库

核心：.env 是配置的『源头』，数据库是运行时的『依据』，两者分工不同。

```js
function syncAdminFlags() {
  const names = String(process.env.ADMIN_USERNAMES || '').split(',').map((s) => s.trim()).filter(Boolean);
  const all = storage.listUsersForAdmin();
  for (const u of all) {
    const should = names.includes(u.username) ? 1 : 0;
    if (u.is_admin !== should) storage.setAdminByUsername(u.username, should);
  }
}
syncAdminFlags(); // 启动时执行
```

为什么鉴权时查库、不查 .env、也不把 is_admin 写进 JWT：
- JWT 发出去后改不了，撤销管理员要等令牌过期才生效
- 查库则撤销即时生效（requireAdmin 每次查库确认 is_admin）
- 标记落库后管理界面能直接显示谁是管理员（🛡），数据库成为唯一运行时依据

于是启动时需要一个『对齐』动作：名单内的标记为管理员，名单外的清掉标记（包括曾经是、后来被移出的）。改 .env 重启即生效，授予和撤销都即时，.env 始终是唯一权威配置源，数据库不会残留过期标记。

## 15.7 中间件流水线：请求的安检

app.use 注册的函数，每个匹配的请求都会先经过它：调 next() 放行，或直接回错误拒绝。多个 use 按注册顺序排队，请求像过安检一样逐个通过。

1. 用户活跃追踪（挂在 /api）：任何请求顺带记录『这个用户刚活跃过』，最近 5 分钟内有请求视为在线，无需前端专门发心跳；从离线转在线时入库一行供管理员回看在线历史。

2. JSON 解析：把请求体的 JSON 文本解析成 JS 对象（req.body）。按路径放宽上限——绘图 40mb（要传参考图 Base64）、办公 20mb（要传图表图片）、其他默认 64kb（防恶意超大请求打爆内存）。

3. 访问口令校验（挂在 /api，带限速）：10 分钟窗口内带错误口令连续 5 次锁 10 分钟；无口令头的探测请求不计失败（浏览器首次访问是正常流程）；验证成功清零计数。只拦 /api，静态页面不拦——页面本身不是秘密，加载后由前端 AccessGate 组件引导输口令。

4. JWT 登录态校验：不是全局挂载，而是按需——需要身份的接口在处理函数里调 userFromRequest(req) 解析验签，无效则回 401；不需要身份的接口（登录、注册、模式列表）就不查。如果把校验全局挂载，游客能访问的接口就全被拦死了。

## 15.8 路由注册与中间件参数

格式：app.动词(路径, 处理函数)。请求到达时 Express 按注册顺序找第一个匹配的路径。

```js
app.post('/api/auth/login', (req, res) => { ... });  // 登录
app.get('/api/modes', (req, res) => { ... });        // 模式列表
```

- app.post 只接 POST（提交数据），app.get 接 GET（要数据），app.delete 接 DELETE（删除）；同一路径可分别注册不同动词各干各的
- req 是请求（能拿请求体、请求头），res 是响应（用它回数据）

管理员接口在路径和业务函数之间塞中间件：

```js
app.get('/api/admin/users', requireAdmin, (req, res) => { ... });
```

请求必须逐个通过：requireAdmin 先跑（解析 JWT → 查库确认 is_admin），不通过直接回 401/403，业务函数根本不执行；通过才放行。业务代码不用关心权限，安检在前头已把不合格请求挡掉。

## 15.9 静态文件托管：URL 如何找到 dist 里的文件

```js
const dist = path.join(__dirname, '..', 'frontend', 'dist');
app.use(express.static(dist));
```

没有任何地方『写』URL 与文件的对应关系，它是 express.static 的机械规则：凡是没被前面路由接住的请求，把 URL 路径直接拼在 dist 目录后面去磁盘找，找到就返回。

```
GET /                          → dist/index.html（/ 对应 index.html 是约定俗成）
GET /assets/index-B3Lkuuh-.js  → dist/assets/index-B3Lkuuh-.js
GET /api/modes                 → 匹配 API 路由，不走 static
GET /favicon.ico               → dist 里没有 → 404
```

## 15.10 哈希文件名与浏览器缓存

构建产物带内容哈希（如 index-B3Lkuuh-.js），内容变一个字指纹就变。引用关系写在 dist/index.html 里，且是 Vite 构建时自动生成的（先打包算哈希定文件名，再生成 HTML 填入引用），人工不可能写错：

```html
<script type="module" crossorigin src="/assets/index-B3Lkuuh-.js"></script>
<link rel="stylesheet" crossorigin href="/assets/index-DcMrQ5s6.css">
```

价值在缓存：浏览器会把静态文件缓存在本地。更新代码后新构建的文件名不同 → 浏览器一看名字没见过就重新下载新版；没变的文件继续用缓存。用户永远拿到最新版，又不用每次下载全部资源。旧哈希文件自然作废（不再被任何 HTML 引用）。

## 15.11 SPA：为什么整个网站装在一个 JS 文件里

浏览器拿到 index.html 后几毫秒内，解析到 script/link 标签就自动请求 JS/CSS（不是用户操作触发，是浏览器解析 HTML 的标准行为）。HTML 里只有一个空 div——整个网站都装在那 255KB 的 JS 里，HTML 只是个壳：提供挂载点 + 指路。

单页应用（SPA）：只返回一次 HTML 壳，之后所有『页面切换』都是 JS 在浏览器里现场渲染。从首页点进文字冒险，浏览器不会再向服务器要新 HTML——JS 收到点击事件后把冒险界面渲染进那个 div，只有数据（API 请求）走网络，所以切换快。

验证方式：浏览器 F12 → Network → 刷新页面，能看到请求顺序：index.html → JS/CSS（浏览器自动）→ API 请求（JS 跑起来后发起，如加载模式列表）。

一个请求的完整旅程（以登录为例）：

```
浏览器 POST /api/auth/login
  → Caddy 反代 → 127.0.0.1:3001
  → trackActivity（记录活跃）
  → express.json（解析请求体）
  → 口令校验（X-Access-Token 对不对？）
  → 命中路由 app.post('/api/auth/login')
  → 业务函数查库验证密码 → 签发 JWT 返回
```

## 0. 阅读前提：先搞懂三层结构

任何"把网页变成 App"的事情，都必须先理解这三层各自的位置：

```
┌─────────────────────────────────────────────┐
│  第一层：界面（前端）                         │
│  Vue 3 + Vite，跑在浏览器里，负责显示与交互    │
├─────────────────────────────────────────────┤
│  第二层：大脑（后端）                         │
│  Express（Node.js），持有 LLM 密钥、裁决逻辑、│
│  存档 data/*.json                            │
├─────────────────────────────────────────────┤
│  第三层：云端 AI（LLM）                       │
│  OpenAI 兼容接口，需要 API Key 鉴权           │
└─────────────────────────────────────────────┘
```

本项目目前的真实链路【事实】：

```
浏览器 :5173 ──代理──▶ Express :3001 ──fetch──▶ LLM 服务
（Vue 前端）      （后端，含 .env 密钥）    （OpenAI 兼容 API）
```

**这里有一个决定全局的事实**：前后端目前是"绑在一起跑在同一台电脑上"的。前端 Vite 开发服务器把 `/api` 请求代理到 `localhost:3001`，而 `localhost` 永远指"当前这台设备"。

→ 手机想玩，第一步不是"做 App"，而是**让手机能访问到这台电脑上跑的服务**。这是后面所有方案分岔的根源。

**第二个关键事实：目前并没有一台"真正的服务器"。** 文档里出现"服务器"一词时，多数场景指的是**你自己电脑上的后端进程**（Express :3001 这个 Node 进程）——它持有 LLM 密钥。更精确的表述是：

> **本项目把"密钥与请求逻辑"分离得很干净**：`.env` 里的 `LLM_API_KEY` 只被本机后端进程（Node/Express）读取，从不进入前端代码。这在**本地自用时天然安全**（别人接触不到你的电脑，也就读不到 `.env`）。

但要注意一个和直觉相反的坑：**"别人看不到密钥" ≠ "别人用不了你的密钥"。** 后端 `/api` 接口本身没有鉴权，一旦你把后端开放到网络（手机连不上本机、需要把监听改成局域网可达，或将来部署到公网），同一网络内的其他人可以直接调用你的 API 接口、消耗你的 LLM 额度——他们不需要看到密钥，只需要能访问接口。所以：

- **局域网个人自用**：安全（外人进不了你的局域网）✅
- **开放公网**：必须加鉴权（令牌/访问口令）+ HTTPS，否则有额度被盗风险 ⚠️

## 1. 先说结论：四条路该怎么选

| 方案 | 一句话描述 | 手机上得到什么 | 推荐度（本项目） |
|---|---|---|---|
| A · PWA（渐进式网页应用） | 把网页升级成"可安装的全屏应用" | 手机桌面图标 + 全屏无地址栏 + 离线壳 | ⭐⭐⭐ 当前阶段首选 |
| B · Capacitor（Web 壳打包） | 用现成 Vue 代码套一个原生外壳 | 真正的 iOS/Android 安装包，可上架商店 | ⭐⭐ 中期目标 |
| C · 微信小程序（Taro） | 把代码转译成小程序格式 | 微信里的小程序入口 | ⭐ 国内微信分发用 |
| D · 原生重写（Swift/Kotlin） | 从零用系统语言重写 | 最"原生"，但没有意义的重投入 | ✗ 不推荐 |

**为什么是 A → B 的递进顺序**：
- A 和 B 用的是**同一套 Vue 代码**。A 是在现有网页上做加法（加 PWA 壳 + 适配手机布局），B 是把做完的网页打包成安装包。**先做 A、后做 B，代码几乎不浪费。**
- C 需要用 Taro 把 Vue 转译，组合式 API 与第三方生态兼容性要额外处理，是独立的一条技术线，和 A/B 不共用。
- D 等于把前端所有页面用 Swift/Kotlin 重写一遍，工作量是 A/B 的数倍，纯粹为了"原生"不值得。

> 一句话记忆：**HTML/CSS/JS 写完的界面，PWA 让它"像 App 一样打开"，Capacitor 让它"真的是个 App"，小程序让它"活进微信里"。**

## 2. 方案 A 详解：PWA（渐进式网页应用）

### 2.1 它是什么

PWA = **Progressive Web App**，是 W3C 标准定义的一整套 Web 能力，让浏览器里的网页具备"接近原生 App"的体验。它不是新框架，不装任何东西，只需要：

| 组成部分 | 作用 | 本项目当前状态 |
|---|---|---|
| `manifest.webmanifest` | 声明 App 名称、图标、主题色、是否全屏 | 无【事实】→ 需新增 |
| Service Worker（`sw.js`） | 拦截网络请求、缓存静态文件，让壳离线也能打开 | 无【事实】→ 需新增 |
| 图标（192px/512px + apple-touch-icon） | 主屏幕图标 | 无【事实】→ 需生成 |
| `theme-color` / `display: standalone` | 顶栏配色、全屏无地址栏 | 无【事实】→ 需配置 |

### 2.2 加了这些之后，手机上得到什么

- 手机浏览器（Chrome/Safari）访问网址 → 菜单里出现"添加到主屏幕" → 主屏出现图标，点击以**独立全屏窗口**打开（没有地址栏），体验接近原生 App。
- iOS 上 Safari 对 PWA 支持良好；Android 上 Chrome 会主动推荐安装。

### 2.3 必须理解的边界（不是缺点，是常识）

- **Service Worker 缓存的只是"壳"（HTML/CSS/JS），AI 对话必须联网。** 本项目是 LLM 驱动的，离线只能看到界面不能玩——这对文字冒险游戏是合理预期，不是缺陷。
- PWA **不能直接上架 App Store / Google Play**（需要包装成签名的安装包，那正是方案 B）。但"添加到主屏幕"对个人使用完全够。
- iOS 的 PWA 有少量限制（如存储配额、部分 API），但对本项目（纯对话 + 本地 JSON 存档在运行后端的机器上）无实质影响。

### 2.4 对本项目的改动清单（真实可执行）

| 改动点 | 涉及文件 | 说明 |
|---|---|---|
| 引入 manifest 与图标 | `frontend/index.html` + 新增 `frontend/public/manifest.webmanifest`、`frontend/public/icons/` | Vite 会自动把 `public/` 下的文件原样复制到构建产物【事实】 |
| 注册 Service Worker | `frontend/src/main.js` | 只在 `import.meta.env.PROD`（生产构建）注册，避免开发期缓存干扰 |
| 主题色与全屏 | `manifest` 里 `display: "standalone"`、`theme_color` | 全屏 + 状态栏配色 |
| 移动端 UI 适配（详见 §5） | 各 `*.vue` 与 `style.css` | 这一步才是重头，PWA 壳本身很轻 |

**工作量估算**：PWA 静态配置本身不到 1 天；真正的时间在 §5 的响应式适配（对 4 个游戏页 + 首页逐个改）。

## 3. 方案 B 详解：Capacitor（Web 壳打包成真 App）

### 3.1 它是什么

**Capacitor** 是 Ionic 团队维护的开源工具，工作原理一句话：**把你的 Web 应用（已构建的 `dist/`）装进一个 WebView，再包上 iOS/Android 的工程外壳，形成一个真正的安装包。**

```
Vue 项目 ├─ npm run build ─► dist/（静态网页）
         └────────────────────────┬─────────► 打包进 WebView（App 内的浏览器内核）
Capacitor CLI ──► iOS 工程(xcodeproj) / Android 工程(Gradle) ──► .ipa / .apk / .aab
```

### 3.2 关键事实：它不重写你的代码

- Vue 组件、路由、状态管理全部原样运行，只是"舞台"从浏览器变成了 App 内嵌的 WebView。
- 由于代码不变，**从方案 A（PWA）升级到方案 B 时，前面做的响应式适配会被 100% 复用。**
- Capacitor 额外提供"原生插件"，如访问摄像头、推送通知、文件系统——本项目用不上这些，只需要最基础的壳。

### 3.3 硬件与环境门槛（真实成本）

| 目标平台 | 必须的软件 | 本机是否具备 |
|---|---|---|
| Android 安装包 | Android Studio（或 Android SDK + Gradle） | 需确认，通常要下载数 GB |
| iOS 安装包 | macOS 电脑 + Xcode + Apple 开发者账号（¥688/年） | 当前是 Linux 系统【事实】，**无法直接构建 iOS** |

- 在本机（Linux）上**可以构建 Android 的 .apk**（通过 Capacitor 加 Android SDK）。
- iOS 承包必须有一台 Mac 和开发者账号——这是 Apple 的硬性规定，任何工具都绕不过。若近期不想花钱/弄 Mac，iOS 放后面。
- 即使不上架，Android 的 .apk 也可以直接发给别人安装（需在系统设置里允许"安装未知来源应用"）。

### 3.4 上架商店的额外事项（很靠后的进度）

- Android 上架 Google Play：需开发者账号（一次性 $25），需签名（`keystore`）。
- iOS 上架 App Store：需开发者账号（¥688/年）、审核流程，且 App 内不能绕过审核规则。
- 本项目的**后端需要部署到公网**（§6），否则别人的手机上 App 连不上你的电脑。

### 3.5 工作量估算

响应式适配之后：装 Capacitor + 初始化 + Android 打包，通常 1~3 天（不含上架审核排队）。

## 4. 方案 C：微信小程序（Taro）——简要说明为什么不是现在

- **Taro** 是一个把 React/Vue 代码编译成微信/支付宝小程序代码的框架。
- 本项目用 Vue 3 组合式 API + 手写 CSS，Taro 支持 Vue 3，但**小程序 CSS 是阉割版**（不支持 `position: fixed` 的一些用法、选择器受限），需要逐页排查兼容性工程，这是一条**与 A/B 不共用的独立投入线**。
- 收益场景是"在微信生态里传播/分享给微信好友"，适合国内社交分发。若你的目标是"手机独立游玩 + 上架"，微信小程序不是必经之路。
- **结论**：技术上可行，但本期不推荐，也不是 A/B 的前置或替代。

## 5. 横切需求：手机 UI 适配（不管选哪条路都要做）

这是工作量最大、也最容易被低估的部分。当前界面是**桌面双栏布局**【事实】：

```
┌───┬────────────────┐
│侧栏│   主区         │   ← 桌面 768px 以上：侧栏 280px + 对话流
└───┴────────────────┘
```

手机屏幕（约 360~430px 宽）按竖屏放不下。需要做的事：

| 当前问题 | 适配方案 |
|---|---|
| 4 个游戏页都有左/右侧栏（角色、身份、在场者、死讯） | 折叠成**顶部图标 + 底部抽屉**，点击展开 |
| 推理杀处刑按钮、狼人杀投票按钮密排 | 改成大触控区（高度 ≥44px，Apple 可访问性指南的通用标准），按钮间距加大 |
| 输入框在页面底部 | 固定于视口底部，键盘弹出时不让遮挡（`visualViewport` 或滚动处理） |
| 首页多列模式选择 | 单列卡片大按钮 |
| 全局文字/行距 | 用 CSS 媒体查询 `@media (max-width: 767px)` 一套规则覆盖，不改变桌面布局 |

**技术实现方式**：当前是纯手写 CSS（无 UI 框架）【事实】，所以用媒体查询逐页加一套移动端样式即可，不引入新依赖。

## 6. 后端部署：本报告的真正分水岭

无论 A/B/C 哪个方案，**手机要能玩，请求必须到达后端**。按部署方式分三个梯队：

### 梯队 1 · 局域网（零成本，个人自用）
- 后端和前端都监听 `0.0.0.0`（而不是只监听 `localhost`，否则手机访问不到）。
- 手机连同一个 WiFi，浏览器访问 `http://电脑局域网IP:5173`。
- 现状：`server/index.js` 的 `app.listen(PORT)` 默认监听所有接口【事实：`app.listen(PORT, ...)` 不传 host 时即监听 0.0.0.0】，Vite 默认只监听 localhost【需改，dev.sh 加 `--host`】。
- 限制：电脑关机就玩不了；出了这个 WiFi 就玩不了。**这是"个人自用为主"场景的完美起步。**

### 梯队 2 · 公网服务器（云部署，分享给别人/上架 App 的前提）
- 一台真正的云服务器（阿里云/腾讯云/轻量应用服务器等），部署后端，绑定域名 + HTTPS。**注意：这与你现在"本机跑后端"是两回事——只有走到这一步，才出现一台可以公网访问的服务器。**
- App/网页通过 `https://你的域名/api/...` 访问，**密钥永远只留在服务器**。
- 需要额外处理：域名 + 证书（Let's Encrypt 免费）、防火墙、进程守护（systemd/pm2）、可选的上限防御（防止别人滥用你的密钥额度）。
- 这是正式"分享/上架"的必经之路，工作量集中在运维而非代码。

### 梯队 3 · Serverless（如 Vercel/Cloudflare Workers）
- 本项目后端是 Express + 本地 JSON 文件存储【事实】，而 Serverless 平台**无持久磁盘**，`data/*.json` 存不住。
- 若要走 Serverless，需把存档改成外部存储（数据库/对象存储），属于架构改动。**本期建议不碰。**

> 结论：**个人自用 = 梯队1足够；将来上架分享 = 做梯队2。** 架构上不需要为"将来上架"提前改任何代码，到时候部署即可。

## 7. 安全与资源常识（低成本但必须知道）

| 项 | 说明 |
|---|---|
| LLM 密钥 | 只放本机后端进程读取的 `.env`（将来部署到云服务器后同理），App 包里绝不能有。本项目现状已满足，保持即可 |
| 你的 API 额度 | 局域网自用安全；一旦开放公网且无鉴权，任何人可调用后端消耗你的 LLM 额度。开放前需加一简单口令/token |
| 存档安全 | 存档在 `data/*.json`（存于运行后端的机器上），局域网自用无风险；部署到云后需注意备份 |
| 手机端无密钥 | PWA/Capacitor 里前端代码可被查看，但里面本来就没有密钥（架构保证） |

## 9. 常见误区澄清（学习要点）

1. ❌ "做 App 就要学 Swift/Kotlin" —— 对本项目是误区。你的界面是 Vue，用 PWA/Capacitor 就能在手机上运行，不必重写语言。
2. ❌ "PWA 就是加个 manifest" —— manifest 是 1/4，真正的工作量在响应式 UI 与服务缓存策略，别被"配置 10 分钟搞定"的说法误导。
3. ❌ "小程序和网页是同一套代码" —— Taro 能转译，但 CSS 能力与组件生态有差异，仍需单独调试，不是白嫖。
4. ✅ "PWA → Capacitor 是同一套代码的复利" —— 这是推荐 A→B 递进的根本原因，前面改的 UI 后面全都用得上。
5. ✅ "后端部署决定成败" —— 手机端技术含量不高，后端能否被手机访问才是一切的前提。先做局域网，再谈云。

## 6. Caddy 反向代理（HTTPS）

```bash
# 安装 Caddy v2（官网二进制方式，APT 官方源在国内不稳定）
sudo cp caddy /usr/local/bin/caddy && sudo chmod +x /usr/local/bin/caddy

# /etc/caddy/Caddyfile：
# {
#   default_sni <公网IP>   # 纯 IP 访问无 SNI，需默认值才能匹配证书
# }
# <公网IP> {
#   reverse_proxy 127.0.0.1:3001
#   tls internal   # 自签证书；绑定域名+备案后可删此行换自动受信任证书
# }

# systemd 服务：/etc/systemd/system/caddy.service（ExecStart=/usr/local/bin/caddy run --config /etc/caddy/Caddyfile）
sudo systemctl daemon-reload && sudo systemctl enable --now caddy
```

## pnpm 构建经验（2026-10-25 补充）

本服务器（Ubuntu, node v20.20.2, npm 10.8.2）上部分开源项目 npm 安装失败：

- billiards（tailuge/billiards）：`npm error Cannot read properties of null (reading 'edgesOut')`，删 lock/清缓存/`--legacy-peer-deps`/npm@8 均无效
- web-jump：npm install 报 `Exit handler never called!`
- yarn 4.x（corepack）安装卡住超时

**解决方案：全局安装 pnpm（`npm install -g pnpm`）后 `pnpm install && pnpm run build`，两个项目均构建成功。**

结论：遇到 npm 安装异常时优先尝试 pnpm，不要在 npm 的各种 flag 上反复消耗时间。
